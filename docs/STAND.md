# Тестовый стенд: инструкция для администратора

Стенд — это копия платформы на арендованном сервере (VPS) с адресом вида `https://stand.ваш-домен.ru`. На нём вы кликаете интерфейс и сами вводите данные объекта. Каждое изменение, попавшее в ветку `main` на GitHub, **само** появляется на стенде через 10–15 минут.

Программировать не нужно. Всё делается в браузере и в окне SSH на вашем компьютере (PowerShell или Терминал): восемь шагов, первый раз — около часа (большая часть уходит на ожидание). Названия кнопок у хостеров немного отличаются — ищите слова, выделенные **жирным**.

> Инструкция работает после того, как изменения этапа 5b слиты в `main` (в ней есть команда, которая скачивает скрипт именно из `main`).

> **Какие данные можно вносить на стенд.** Пока не закрыт вопрос Q-32 (договор-поручение и уведомление Роскомнадзора), объект, арендаторы и лимиты вносятся настоящие, а **люди и номера машин — только выдуманные**. Настоящие данные людей — после решения по Q-32.

**Что понадобится заранее**
- доступ **администратора** к репозиторию `INDIGOPROGRAMMER-ai/oxrana` на GitHub (нужна вкладка **Settings**);
- доменное имя и доступ к его DNS-настройкам (у регистратора или в панели DNS);
- банковская карта для оплаты сервера;
- ваш рабочий e-mail (Let's Encrypt шлёт на него служебные письма);
- компьютер с Windows 10/11 или macOS (для окна SSH).

## Шаг 1. Заказать сервер у хостера

Подойдёт любой российский хостер с виртуальными серверами (VPS/«облачный сервер»). Параметры:

| Что выбрать | Значение |
|---|---|
| Расположение | желательно Россия; рабочий стенд заказчика — Timeweb, Амстердам (в РФ не нашлось ресурсов). Для стенда это допустимо, пока в нём только выдуманные люди и номера (Q-62) |
| Операционная система | **Ubuntu 24.04** (именно 24.04, не 22.04 и не 25.x) |
| Процессор / память | от 2 vCPU и 4 ГБ RAM |
| Диск | от 40 ГБ, SSD/NVMe |
| Публичный IPv4-адрес | обязательно, один |
| Доступ | **ваш ключ SSH** (поле «SSH-ключ» при заказе; как его получить — ниже) и пароль root на всякий случай |
| Резервные копии/снимки хостера | по желанию, это отдельно от нашей ночной копии базы |

**Зачем ключ SSH.** Скрипт шага 3 отключает вход на сервер по паролю (так безопаснее), и дальше по SSH пускают только по ключу. А из веб-консоли хостера (VNC) текст обычно нельзя скопировать — ни ключ для GitHub, ни ссылку из шага 6. Поэтому работаем из окна SSH на своём компьютере, а веб-консоль оставляем на крайний случай.

Как получить ключ (один раз, на своём компьютере):
- **Windows 10/11:** откройте **PowerShell** и выполните `ssh-keygen -t ed25519` — на все вопросы нажмите Enter. Затем `Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub` — это одна строка, начинается с `ssh-ed25519`.
- **macOS:** откройте **Терминал**, выполните `ssh-keygen -t ed25519` (Enter на все вопросы), затем `cat ~/.ssh/id_ed25519.pub`.

Эту строку (открытый ключ, его можно показывать) вставьте при заказе в поле **SSH-ключ**. Файл `id_ed25519` без `.pub` — закрытый ключ, его никому не отправляйте.

Если хостер не даёт добавить ключ при заказе: подключитесь по паролю (`ssh root@IP`) и до шага 3 выполните на сервере `mkdir -p ~/.ssh && chmod 700 ~/.ssh && echo "ВАШ_ОТКРЫТЫЙ_КЛЮЧ" >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys`. Затем **проверьте**, что вход по ключу работает: откройте второе окно и выполните `ssh root@IP` — пароль спрашивать не должен.

**Скрипт шага 3 сам останавливается, если в `/root/.ssh/authorized_keys` нет вашего ключа**: он ничего не меняет и печатает, как добавить ключ. Так сделано потому, что отключение входа по паролю без ключа запирает вас на сервере (остаётся только веб-консоль хостера). Добавьте ключ и запустите ту же команду ещё раз.

После заказа в панели хостера найдите и запишите:
- **IP-адрес сервера** (четыре числа через точки, например `203.0.113.15`);
- **пароль root** (или кнопку «сбросить пароль»);
- кнопку веб-консоли: она называется **Консоль**, **VNC**, **Веб-консоль** или **Открыть терминал** — запасной вход, если SSH не работает.

Если в панели есть раздел **Брандмауэр / Firewall / Группы безопасности**, проверьте, что разрешены входящие **22, 80 и 443** (TCP). Чаще всего по умолчанию открыто всё.

## Шаг 2. Привязать домен к серверу (DNS)

Нужна **одна** запись. Откройте управление DNS у того, кто обслуживает ваш домен, и добавьте:

| Поле | Значение |
|---|---|
| Тип записи | **A** |
| Имя / Хост | `stand` (получится `stand.ваш-домен.ru`; можно другое слово, например `pass`) |
| Значение / Указывает на | IP-адрес сервера из шага 1 |
| TTL | 300 (5 минут) или «авто» |

Пост охраны и кабинет работают на этом же адресе (кабинет — `https://stand.ваш-домен.ru/`, пост — `https://stand.ваш-домен.ru/gate/`), отдельные записи не нужны.

Проверка: через 5–30 минут откройте на любом компьютере с Windows командную строку и выполните `nslookup stand.ваш-домен.ru` — в ответе должен быть IP вашего сервера. (Если команда пишет «не найден» — подождите ещё.) Дальше этот шаг можно не ждать: на шаге 3 скрипт сам проверит запись и скажет, если она ещё не готова.

## Шаг 3. Настроить сервер одной командой

1. На своём компьютере откройте **PowerShell** (Windows) или **Терминал** (macOS) и подключитесь: `ssh root@IP_СЕРВЕРА`. На вопрос «Are you sure you want to continue connecting» ответьте `yes`. Если ключ не добавлен — спросит пароль root (символы не отображаются — это нормально).
2. Скопируйте команду ниже, **замените** `stand.ваш-домен.ru` на ваш адрес из шага 2, а `вы@почта.ru` — на ваш e-mail:

   ```
   curl -fsSL https://raw.githubusercontent.com/INDIGOPROGRAMMER-ai/oxrana/main/deploy/setup-vps.sh | bash -s -- stand.ваш-домен.ru вы@почта.ru
   ```

3. Вставьте её в окно SSH (правая кнопка мыши или **Ctrl+V** / **Cmd+V**) и нажмите **Enter**.

   Если команда сразу падает с ошибкой скачивания (`curl: (28)`, `(35)`, `(7)`) — из РФ сервер GitHub с файлами временами недоступен. Тогда выйдите с сервера (`exit`) и запустите настройку со своего компьютера — файл скачает ваш компьютер, а выполнит сервер. В Windows — в **Командной строке** (cmd, не PowerShell), в macOS — в Терминале:

   ```
   curl -fsSL https://raw.githubusercontent.com/INDIGOPROGRAMMER-ai/oxrana/main/deploy/setup-vps.sh | ssh root@IP_СЕРВЕРА "bash -s -- stand.ваш-домен.ru вы@почта.ru"
   ```
4. Подождите 3–6 минут. Скрипт выводит шаги («==> Пакеты», «==> Docker» …). Он безопасен для повторного запуска: если что-то оборвалось (например, пропал интернет), просто запустите ту же команду ещё раз.
5. В конце появится рамка **«СЕРВЕР НАСТРОЕН»** и блок **«ЧТО ВСТАВИТЬ В GITHUB»**. Не закрывайте окно, пока не выполните шаг 4.

Что скрипт сделал на сервере: создал пользователя `deploy` для автоматических обновлений (без прав администратора), поставил Docker (если связь с серверами Docker из вашей сети ненадёжна — повторите команду, шаги идемпотентны), закрыл все входящие порты кроме 22, 80 и 443, отключил вход по SSH-паролю (только по ключу), включил защиту от перебора паролей (fail2ban) и автоматические обновления безопасности (при необходимости сервер сам перезагрузится ночью около 03:30 UTC и поднимется), добавил swap, поставил время UTC, настроил ночную копию базы.

Если в рамке написано **«ВНИМАНИЕ: домен … не указывает …»** — вернитесь к шагу 2, поправьте запись и подождите; повторно запускать скрипт не обязательно.

## Шаг 4. Добавить секреты в GitHub

Эти четыре значения GitHub будет использовать, чтобы заходить на сервер и обновлять стенд. Их выводит скрипт в конце шага 3.

1. Откройте `https://github.com/INDIGOPROGRAMMER-ai/oxrana`.
2. Вверху нажмите вкладку **Settings** (если её нет — у вас нет прав администратора).
3. Слева: **Secrets and variables** → **Actions**.
4. Вкладка **Secrets** → кнопка **New repository secret**. Добавьте три секрета, у каждого — поле **Name** и поле **Secret**, затем **Add secret**:

   | Name | Что вставить в Secret (берётся из блока в консоли) |
   |---|---|
   | `STAND_HOST` | IP-адрес сервера |
   | `STAND_KNOWN_HOSTS` | одна строка вида `203.0.113.15 ssh-ed25519 AAAA…` |
   | `STAND_SSH_KEY` | **весь** текст ключа: от строки `-----BEGIN OPENSSH PRIVATE KEY-----` до строки `-----END OPENSSH PRIVATE KEY-----` включительно |

5. Вкладка **Variables** (рядом с Secrets) → **New repository variable**: **Name** `STAND_DOMAIN`, **Value** — ваш адрес (например, `stand.ваш-домен.ru`) → **Add variable**.

Как переносить значения: выделите текст в окне SSH мышью и скопируйте и нажмите Ctrl+C (Windows) или Cmd+C (macOS) — сразу в GitHub, без чатов и почты. Ключ копируйте целиком, включая первую и последнюю строки.

### Ключ деплоя в секрете GitHub

Ключ, скопированный мышью из окна PowerShell, часто портится: в конце строк остаются пробелы и невидимые символы возврата каретки, по краям — пустые строки. Деплой такой ключ сам очищает от пробелов и пустых строк и перед подключением проверяет его (`ssh-keygen -y`). Если проверка красная, в журнале будет сообщение «Секрет STAND_SSH_KEY …» вместо непонятного `error in libcrypto`:

- **«вставлен не целиком»** — в значении нет строки `-----BEGIN OPENSSH PRIVATE KEY-----` или `-----END OPENSSH PRIVATE KEY-----`. Скопируйте блок заново, от первой строки до последней.
- **«не читается как ключ»** — ключ повреждён при копировании или это не тот файл (нужен закрытый ключ деплоя из блока в консоли сервера, а не ваш личный и не `.pub`). Напечатайте блок снова (повторите команду шага 3 — она идемпотентна) и вставьте в секрет заново. Если мышью не выходит — используйте веб-интерфейс GitHub в том же окне: выделите блок в SSH-окне, Ctrl+C, откройте секрет → **Update** → Ctrl+V.

Когда всё добавлено, очистите окно командой `clear` и не пересылайте ключ никому: он даёт доступ к серверу. Если ключ попал не туда — на сервере выполните `rm /root/.oxrana/deploy_key`, затем ту же команду из шага 3 (будет выпущен новый ключ, старый перестанет работать) и обновите секрет `STAND_SSH_KEY`.

## Шаг 5. Запустить первый деплой

1. В репозитории откройте вкладку **Actions**.
2. Слева в списке выберите **Деплой стенда**. (Если GitHub предложит включить workflows — подтвердите.)
3. Справа нажмите **Run workflow** (кнопка с выпадающим окном).
4. В окне: **Use workflow from** — оставьте ветку `main`; в поле **Что сделать** — `deploy`; поле про версию отката оставьте пустым → нажмите зелёную кнопку **Run workflow**.
5. Обновите страницу — появится строка с жёлтым кружком (идёт). Нажмите на неё, затем на задание **Деплой на стенд**, чтобы смотреть ход выполнения.
6. Первый раз это занимает 10–15 минут: сборка образов, передача на сервер, получение сертификата. Успех — **зелёная галочка** и в конце строка «Готово: стенд работает на версии …».
7. Откройте `https://stand.ваш-домен.ru` — должна появиться страница входа. Адрес поста — `https://stand.ваш-домен.ru/gate/`.

Если запуск **красный**, откройте шаг, помеченный красным крестиком, и прочитайте последние строки. Частые причины:

| В журнале написано | Что делать |
|---|---|
| `Не заданы секреты STAND_HOST…` | Шаг 4: не хватает секрета (проверьте все три имени, без пробелов) |
| `Host key verification failed` | Секрет `STAND_KNOWN_HOSTS` неверный или относится к другому IP — возьмите строку из блока в консоли (шаг 3; блок можно напечатать снова повтором команды) |
| `Секрет STAND_SSH_KEY вставлен не целиком` / `не читается как ключ` | Раздел «Ключ деплоя в секрете GitHub» (шаг 4) |
| `Permission denied (publickey)` | Ключ читается, но сервер его не принимает: это не тот ключ, или шаг 3 выполнялся заново и выпустил новый (обновите секрет) |
| `Connection timed out` | Неверный `STAND_HOST` или хостер блокирует порт 22 (шаг 1, брандмауэр) |
| `не ответил версией … за отведённое время` и совет про DNS | A-запись из шага 2 ещё не работает или указывает на другой адрес. Исправьте, подождите, запустите деплой ещё раз |
| `Миграции не применены` | Ошибка в самой новой версии программы. Стенд остался на прежней версии. Сообщите разработчикам, приложив журнал |

Повторный запуск безопасен: можно нажимать **Run workflow** сколько угодно раз.

## Шаг 6. Чистый старт: организация и владелец

Стенд стартует **пустым**: в нём нет ни объекта, ни пользователей. Нужно создать организацию и первого пользователя — владельца.

1. Подключитесь к серверу, как в шаге 3: `ssh root@IP_СЕРВЕРА`.
2. Выполните команду:

   ```
   oxranactl bootstrap
   ```

3. Ответьте на вопросы (Enter подтверждает значение в квадратных скобках). **Каждый ответ проверяется сразу**: если ввели лишнее или ошиблись (например, вместо часового пояса написали `yes`), команда объяснит, что не так, и спросит снова — вводить всё заново не придётся:
   - **Название организации** — как оно будет показано в системе (если консоль не принимает русские буквы с клавиатуры — вставьте текст из буфера);
   - **Короткое имя латиницей** — от 3 символов: маленькие латинские буквы, цифры и дефис, например `integraciya`;
   - **Часовой пояс объекта** — адрес вида `Область/Город`; для Челябинска `Asia/Yekaterinburg` (уже подставлен, на вопрос достаточно нажать Enter; ответ `yes` не подойдёт);
   - **ФИО владельца** и **e-mail владельца** — e-mail станет логином.
4. Проверьте сводку и ответьте `д` (да).
5. На экране появится одноразовая **ссылка установки пароля**, вида `https://stand.ваш-домен.ru/password#…`. Она показывается **только здесь**, нигде не сохраняется и действует 3 суток. Откройте её в браузере, придумайте пароль (не короче 10 символов, не только цифры) → вы автоматически войдёте в кабинет владельца.

Если ссылка потерялась или истекла: `oxranactl bootstrap --new-owner-link --owner-email e-mail-владельца` — команда выдаст новую.

Дальше всё делается в кабинете: **Пользователи и приглашения** → пригласить сотрудника → система показывает ссылку приглашения **один раз** — передайте её человеку сами (письма пока не отправляются). Устройство поста привязывается в разделе **Устройства КПП**.

Важно про безопасность: ссылку установки пароля не публикуйте в общих чатах и передавайте только владельцу. В журналы GitHub она не попадает — чистый старт запускается только вручную на сервере.

## Шаг 7. Как стенд обновляется

- Каждое слияние (merge) в ветку `main` после успешной проверки (CI) само запускает **Деплой стенда**. Следить: вкладка **Actions** → **Деплой стенда**. Зелёная галочка — стенд на новой версии, красный крестик — стенд остался на прошлой (сервер проверяет себя после обновления и сам откатывается).
- Пока вы не выполнили шаг 4, после каждого слияния появляется жёлтая пометка «Стенд не настроен», это нормально.
- Номер версии стенда (дата и код коммита) виден в конце журнала деплоя и в консоли: `oxranactl status`.
- Во время перезапуска программа недоступна от нескольких секунд до минуты; пользователей обновление не разлогинивает.

## Шаг 8. Как откатить

**Кнопкой на GitHub (одна кнопка):** вкладка **Actions** → **Деплой стенда** → **Run workflow** → в поле **Что сделать** выберите `rollback` → **Run workflow**. Стенд вернётся на предыдущую версию. Чтобы вернуться на конкретную версию, впишите её номер (например, `20261012-ab12cd3`) в поле «версия, на которую вернуться». Номера предыдущих версий видны в `oxranactl status` и в журналах прошлых деплоев.

**Командой на сервере (консоль хостера, root):**

```
oxranactl rollback
```

Повторный `oxranactl rollback` возвращает стенд обратно на новую версию.

Что откат не делает: **данные не откатываются** — вернуть вчерашнюю базу можно только из копии (раздел «Копии» ниже). Базу меняют миграции, а они всегда совместимы с версией назад, поэтому прежняя версия программы работает на новой базе.

Если новая версия сломана, а вы не знаете, откатываться ли, — откатывайтесь: вернуться вперёд всегда можно новым деплоем.

## Логи и состояние

В консоли хостера (root) или по SSH под `deploy`:

| Команда | Что показывает |
|---|---|
| `oxranactl status` | версию, предыдущую версию, контейнеры, дату последней ночной копии |
| `oxranactl health` | отвечает ли стенд сейчас (то же, что проверяет деплой) |
| `oxranactl logs` | последние 200 строк журнала программы (api) |
| `oxranactl logs api 1000` | последние 1000 строк журнала программы |
| `oxranactl logs proxy` | журнал входящих запросов и сертификатов (Caddy) |
| `oxranactl logs postgres` | журнал базы данных |

В журналах программы нет паролей, ссылок и персональных данных; журнал Caddy не содержит cookie, токенов и строки запроса (в ней бывают номера машин). Журналы деплоев — на GitHub: **Actions** → **Деплой стенда** → нужный запуск.

## Копии базы

- Каждую ночь в 02:00 UTC (07:00 по Челябинску) сервер делает копию базы и хранит **7 последних**. Перед каждым обновлением делается ещё одна («pre-update», хранятся 3 последних).
- Лежат на этом же сервере: `/opt/oxrana/backups/` (файлы `daily-ГГГГММДД-ЧЧММСС.dump`). Права только у пользователя `deploy` и root.
- Сделать копию сейчас: `oxranactl backup`.
- Восстановить базу из копии (**текущая база будет заменена**; перед этим автоматически делается страховочная копия):

  ```
  ls /opt/oxrana/backups
  oxranactl restore /opt/oxrana/backups/daily-ГГГГММДД-ЧЧММСС.dump --yes
  ```

Копии на том же сервере не защитят, если сервер пропадёт целиком. Копирование на внешнее хранилище — этап 12. Пока можно включить автоматические снимки диска в панели хостера.

## Чего стенд пока не умеет

- Письма и SMS не отправляются: ссылки приглашений и сброса пароля показывает администратору сам кабинет (он передаёт их человеку).
- Нет мониторинга: если стенд «лёг», узнаете, открыв адрес. Проверить причину — `oxranactl status` и `oxranactl logs`.
- Копии — только на самом сервере (см. выше).
- Персональные данные: договор-поручение и уведомление РКН пока не оформлены (вопрос Q-32). Пока они не оформлены, разумно вводить объект, арендаторов и лимиты настоящими, а людей и номера машин — выдуманными; решение о том, вносить ли настоящие данные людей, принимаете вы как оператор.

## Если что-то пошло не так

| Симптом | Что делать |
|---|---|
| Сайт не открывается | `oxranactl status` — все три сервиса (`postgres`, `api`, `proxy`) должны быть `running`. Если `proxy` перезапускается — `oxranactl logs proxy` (чаще всего это DNS: адрес указывает не на этот сервер) |
| «Ваше подключение не защищено» | Сертификат ещё не выдан: подождите 1–2 минуты после первого деплоя; если не проходит — проверьте A-запись (шаг 2) и что порты 80 и 443 открыты у хостера |
| Деплой красный | Таблица в шаге 5 |
| Забыли пароль владельца | `oxranactl bootstrap --new-owner-link --owner-email e-mail-владельца` |
| Нужно начать с пустой базы | Сообщите разработчикам: команда удаляет все данные, поэтому здесь не приведена |
