### 3.5 КПП (Checkpoint) `[✓ 23, 26]`

Вкладка КПП объекта. Колонки списка: **Название · Адреса · Типы транспорта**.

Форма создания:
| Поле | Тип |
|---|---|
| Название | text |
| Добавить адрес | мультивыбор, «Не выбрано ни одного адреса» |
| Добавить тип транспорта | мультивыбор, «Не выбрано ни одного типа транспорта» |

**КПП — это не просто пост охраны, а маршрутизатор потока:** он описывает, какие адреса обслуживает и какой транспорт через него проходит. Для логистического центра логично: `КПП-1 Грузовой въезд` (грузовые + фуры, адреса складов), `КПП-2 Офисный` (легковые, адреса офисов). Охранник, привязанный к КПП, видит только свой поток.

**КПП — обязательное предусловие** для заведения учётки охранника: в форме сотрудника дропдаун КПП иначе пуст.

---

**Назначение дословно от вендора:** «этот раздел служит для **разделения пропусков по адресу и типу транспорта**» `[transcripts/01]`. КПП — фильтр видимости пропусков для охраны, а не физическое устройство.

Редактирование и удаление КПП — через три точки справа от строки. Колонки списка: Название · Адреса · Типы транспорта (длинные списки схлопываются в «…и N д.») `[✓ 75, 78]`.

### ⚠ Валидация: обязательно хотя бы одно из двух `[✓ 76]`

Пустой КПП создать нельзя. Сообщение сервера: **«Поле addresses обязательно для заполнения, когда vehicle types не указано»**. Поля при этом красным заранее не помечаются — валидация срабатывает на сохранении, как и везде в этой платформе.

### ⚠⚠ Механика фильтра — три правила, проверены на живом охраннике

**Правило 1. Фильтр по типу транспорта работает по пересечению.** Пропуск виден охраннику, только если тип транспорта пропуска есть в списке КПП `[✓ 104 → 105]`. КПП-1 с типами Грузовой/Фура/Спецтехника не показал пропуск на `Audi / Легковой`; после добавления `Легковой` пропуск появился.

⇒ **Забыл тип в списке КПП — машины этого типа для поста не существуют.** Охрана будет отвечать «пропуска нет», хотя он есть.

**Правило 2. Пешеходные пропуска НЕ видны на КПП, где указан хоть один тип транспорта** `[✓ 107, 108, 109]`. У пешеходного пропуска типа транспорта нет вообще ⇒ пересечение пустое ⇒ пропуск отсекается. Админ видел 2 пропуска, охранник — 1.

⇒ **Перечислить все типы транспорта НЕ помогает** — пешеход не подпадёт ни под один. Единственный способ показать пешеходов: **не указывать типы вообще**, только адреса.

**Правило 3. Несколько КПП у одного сотрудника дают ПЕРЕСЕЧЕНИЕ, а не объединение** `[✓ проверено 10.08.2026]`. Охранник, привязанный к КПП с адресами и к КПП с типами, увидел **ноль** пропусков. Поведение контринтуитивное: добавляя второй пост, человек ожидает видеть больше, а видит меньше.

⇒ Множественная привязка годится только чтобы **сузить** видимость (например «фуры, едущие в складскую зону»), но не чтобы объединить два потока.

**Правило 4. Адреса и типы внутри ОДНОГО КПП складываются через «И»** `[✓ 152 → 153]`. Проверено чисто: КПП-1 = адрес `ZZZ-ТЕСТ Бокс А-12` + тип `Фура`; на этом адресе лежало пять пропусков, из них одна фура. Охранник увидел **1**. Пропуск виден, только если его адрес есть в списке КПП **И** его тип транспорта есть в списке КПП.

⇒ **Пустой список означает «не фильтровать», а не «ничего не пропускать».** Отсюда же становится понятен прежний результат со скрина 109: пешеходы там появились не потому, что «адреса включают всех», а потому что список типов был очищен и фильтр по типу перестал применяться. И отсюда же — смысл валидации «хотя бы одно из двух»: КПП с двумя пустыми списками показывал бы вообще всё.

### Следствие: конструкция КПП для «Радонежского»

На объекте три физических поста:
1. фуры и руководство;
2. весь остальной транспорт **и** пешеходы;
3. офис, только люди.

Второй пост требует одновременно фильтра по типам (чтобы фура не попала) и видимости пешеходов — а это в системе взаимоисключающие вещи. **Штатного решения нет.** Рабочий обход — две учётные записи на один пост, открытые в двух браузерах:

| КПП | Настройка | Учётка | Статус |
|---|---|---|---|
| КПП-1 Грузовой | типы: Фура | охранник-1 | ✅ собран `[✓ 156]` |
| КПП-2 Транспорт | типы: Легковой · Малотоннажный · Грузовой · Автобус · Спецтехника · Прочее | охранник-2, окно 1 | ✅ собран `[✓ 156]` |
| КПП-2 Пешеходы | адреса: все, типы НЕ указывать | охранник-2-пеший, окно 2 | ⬜ ждёт реальных адресов |
| КПП-3 Офис | адреса: офисные, типы НЕ указывать | охранник-3 | ⬜ ждёт реальных адресов |

**Проверено на стенде 11.08.2026** `[✓ 154, 155]`: охранник-1 на КПП-1 видит только фуру (`1`), охранник-2 на КПП-2 видит четыре легковых и грузовой (`4`). Пересечения нет, потоки разделены.

⚠ **Типы транспорта в КПП-1 «+ Легковой для руководства» — от идеи отказались.** У КПП-1 нет адресов, фильтр только по типу; добавив Легковой, пост увидит **все** легковые пропуска объекта, включая те, что едут на КПП-2. Пропадает главный сигнал «нет в списке = не твой пост». Руководству — постоянные пропуска, вопрос решается на месте.

⚠ **Адресные КПП переживут импорт хуже типовых.** КПП-2 Пешеходы и КПП-3 Офис требуют перечисления конкретных адресов, поэтому собираются только после массового импорта и согласования стандарта короткого названия. Типовые КПП импорт не затрагивает.

Почему нельзя проще (КПП-2 без типов, «фуры отсекаем глазами»): у фуры к боксу А-12 пропуск валиден, охранник найдёт его по номеру, увидит корректную карточку — и ничто в интерфейсе не подскажет, что машина приехала не на тот пост. Отметит «Приехал», система засчитает въезд. **Отсутствие пропуска в списке — единственный надёжный сигнал «не твой пост».**

Цена обхода: охранник помнит, в каком окне искать; журнал действий раздваивается по двум учёткам. Приемлемо — время и пост в журнале есть, кто на смене знает охранная организация.

Руководство: постоянные пропуска на все КПП, отдельный тип транспорта под них заводить не потребовалось.

### 3.5.1 Группы прав сотрудников `[✓ 77, 79-98]`

Раздел **Права** в левом меню. Отображается деревом: карточка группы + аватарки входящих сотрудников + иконки действий (корзина, шестерёнка, `↳` создать дочернюю).

**Предустановленных ролей НЕТ.** На стенде существует единственная группа «Администраторы» с пятью учётками. Документация вендора про четыре готовые роли (супер-администратор, администратор, менеджер по безопасности, охранник) стенду не соответствует — группы под охрану создаются вручную.

**Группы иерархические.** Новая создаётся дочерней от существующей, отсюда уровень «Наследует от родительской группы».

⚠⚠ **Свежесозданная дочерняя группа имеет ПОЛНЫЕ права родителя.** Все дропдауны по умолчанию в «Наследует», родитель — «Администраторы». Посадив охранника на такую группу не глядя, вы даёте ему право менять настройки объекта, удалять пользователей и редактировать права.

**Экономия времени:** `Доступ к модулю = Запрещён` гасит все подпункты модуля — они становятся серыми и нередактируемыми `[✓ 96]`. Проходить каждый подпункт не нужно, достаточно закрыть модуль целиком. ⚠ Но подпункты при этом остаются в значении «Наследует», а не переписываются в «Запрещён» — если позже открыть доступ к модулю обратно, они окажутся администраторскими.

**«Сканер QR» — отдельный модуль прав** ⇒ сканер есть в самом веб-интерфейсе, не только в PASS24.admin и guard.

#### Значения дропдаунов

Общие: `Наследует от родительской группы` · `Запрещён` · `Разрешён`.

**Модуль «Пропуска», Создание** при значении «Разрешено» разворачивается в три тумблера `[✓ 94]`: создавать одноразовые / временные / постоянные. Право дробится по типам, как и в настройках объекта.
⚠ Это право работает **поверх** настройки объекта, а не вместо неё. Если в объекте «Разрешить создание временных пропусков для сотрудников» = `Запретить`, включённый тумблер ничего не даст. Два независимых уровня, оба должны разрешать.

**Модуль «Пропуска», Редактирование** — четыре значения `[✓ 95]`: `Наследует` · `Запрещён` · **`Только статус`** · `Разрешено полностью`.

#### ⚠⚠⚠ Рабочей настройки прав охраны НЕ СУЩЕСТВУЕТ

Проверены оба осмысленных значения, ни одно не годится:

| Значение | Что получаем |
|---|---|
| **`Только статус`** | **не работает** — охранник открывает форму и правит всё подряд, включая адрес, пользователя, тип и даты, и успешно сохраняет `[✓ 111, 142, 143]` |
| **`Запрещён`** | гаснет **и кнопка «Приехал»** `[✓ 146]` — охранник не может отметить въезд, то есть не может работать вообще |

⇒ **Смена статуса в этой системе — частный случай редактирования, а не отдельное право.** Либо пост бесконтрольный, либо бессильный.

**На стенде оставлено `Только статус`** — с ним пост хотя бы функционирует. Кнопка «Приехал» после возврата значения ожила `[✓ проверено 11.08.2026]`.

⚠ Это **блокирует сдачу объекта в эксплуатацию**: регламент поста строится на том, что охрана не переписывает пропуска, а обеспечить это нечем. Раздел 25, вопросы 1 и 2.

#### Ловушка: право «Доступ к модулю» влияет на чужие формы

Запретив доступ к модулю **Сотрудники**, администратор перестаёт видеть группы прав в выпадающем списке при заведении сотрудника `[✓ 99]` — группа существует, но недоступна для выбора. Пришлось открыть доступ к модулю, и вместе с ним охранник получил видимость всего персонала с почтами `[✓ 102]`.

⇒ Право «видеть раздел» распространяется не только на раздел, но и на использование сущности в других формах. Обходится тем, что админ выдаёт группу при создании сотрудника, а потом закрывает модуль обратно.

### 9.7 ⚠⚠⚠ Редактирование пропуска — ДВА БЛОКИРУЮЩИХ ДЕФЕКТА

Разобрано 11.08.2026. **Практический вывод: пропуск после создания не редактируется. Нужны изменения — закрыть и выпустить новый.**

#### Дефект 1. Правка молча меняет тип транспорта на «Легковой»

Форма «Редактирование пропуска» подставляет в поле типа транспорта **дефолт `Легковой`** вместо сохранённого значения и при сохранении записывает его.

Воспроизведено дважды, независимо, на разных пропусках и под разными учётками:

| Пропуск | Было | Кто правил | Что менял | Стало |
|---|---|---|---|---|
| `E555EE` | **Спецтехника** | охранник Петров | только комментарий | **Легковой** `[✓ 142]` |
| `T111TT` | **Фура** | администратор | только комментарий | **Легковой** `[✓ 145]` |

Цепочка по `E555EE` прослежена от источника: телефон арендатора (Спецтехника `[✓ 138]`) → карточка запроса № 4 (Спецтехника `[✓ 139]`) → список до правки (Спецтехника) → список после правки (**Легковой** `[✓ 142]`).

**Дефект платформенный, не контурный** — воспроизводится и у охраны, и у администратора. Правами не лечится, регламентом не лечится.

⚠ **Последствие на логоцентре:** любой комментарий, дописанный на посту, выбивает фуру из КПП-1 по правилу 1 (фильтр по типу). Пропуск при этом остаётся валидным и видимым администратору — заметить порчу нечем, кроме истории событий.

**Чего дефект НЕ затрагивает:**
- при **создании** пропуска подмены нет — `Фура` записалась корректно `[✓ 151]`;
- даты не портятся: у временного `E555EE` период `16:28 → 14.08 00:00` уцелел, хотя дефолт был бы +720 ч;
- след в истории событий остаётся: «Пропуск изменён» с актором и временем `[✓ 143]`.

`[?]` Иногда форма подгружает верное значение — после F5 у `T111TT` стояли корректные `Фура` и `23:55` `[✓ 141]` против дефолтных `Легковой` и `+24 ч` в другой момент `[✓ 140]`. Механизм не установлен; на исход сохранения это не влияет — записывается всё равно `Легковой`.

#### Дефект 2. После наступления времени начала пропуск не редактируется вообще

Сервер валидирует «дата начала ≥ сейчас» **не только при создании, но и при каждом сохранении правки**:

> «Неверные данные: Дата в поле Дата начала должна быть после или равной 2026-08-11 14:12:00» `[✓ 136]`

При этом **первое поле даты в форме редактирования недоступно** — календарь не открывается, значение не меняется `[✓ проверено 11.08.2026]`. Выполнить требование сервера нечем.

⇒ **Как только время начала наступило, пропуск заперт навсегда.** Ни продлить срок, ни исправить цифру в номере, ни дописать комментарий. Фура на воротах с опечаткой в ГРЗ — только перевыпуск.

#### Регламент для «Радонежского»

> Пропуск после создания не редактируется. Нужны изменения — закрыть и выпустить новый.
> Если арендатор указал неверный тип транспорта — **отклонять запрос до одобрения**, а не править после.

⚠ Обеспечить это правами **нечем** — см. 3.5.1: `Только статус` не работает, `Запрещён` убивает кнопку «Приехал».

### 9.8 Лимиты и блокировка по превышению времени

Разобрано 11.08.2026.

#### Лимит активных пропусков — НА ПОЛЬЗОВАТЕЛЯ

Настройка «Лимит разовых / временных / постоянных» в блоке «Работа с пропусками» считается **по пользователю-субъекту пропуска**, а не по объекту и не по адресу.

Доказано матрицей `[✓ 158, 163, 164, 165]`:

| Тест | Условия | Результат | Что доказывает |
|---|---|---|---|
| 1 | Иванов исчерпал лимит, создаём Санычу на адрес Б-7 | создался | лимит **не на объект** |
| 2 | Саныч 0 пропусков, создаём на адрес 1 | создался | ничего (при нуле любой вариант дал бы то же) |
| 3 | Саныч 1 пропуск на адресе 1, создаём ему на **Б-7** | **«Исчерпан лимит активных пропусков»** | лимит **на пользователя**, не на адрес |

⚠ **Администратор не может обойти лимит**, оформив пропуск за арендатора вручную — считается субъект, а не автор.

⇒ **Ограничить компанию этой настройкой нельзя.** У арендатора с тремя логистами квота утраивается. Для требования «не больше N машин у арендатора» настройка не годится ни в каком виде — она считает выданные пропуска, а не машины на территории.

`[?]` Не выяснено, входит ли статус «Просрочен» в понятие «активный». На потоке существенно: забытые просроченные съедят квоту живому человеку.

#### Блокировка по превышению времени нахождения

Поле «Минуты» у опции объекта (Разгрузка, Погрузка и т.д.) = норматив времени на территории. Механика собрана целиком:

| Параметр | Поведение |
|---|---|
| **Триггер** | машина со статусом «На территории» превысила «Минуты» своей опции |
| **Область** | **пользователь** — блокируются ВСЕ пропуска нарушителя, включая ещё не въехавшие |
| **Кого не задевает** | других пользователей, даже на том же адресе |
| **Уведомление** | «Пропуск превысил время нахождения на территории» + кнопка ОТРЕАГИРОВАТЬ, открывающая пропуск. Приходит **и администратору, и охране на всех КПП** |
| **Отображение** | красная надпись **«Заблокирован»** в карточке пропуска |
| **Снятие** | **автоматически** по отметке «Уехал» на пропуске-нарушителе |
| **Автозакрытие** | **нет** — нарушитель остаётся «На территории» до ручной отметки |

Доказательство области `[✓ 169]`: нарушитель `О111ОО174` (Иванов, адрес 1). Заблокированы все пропуска Иванова. **`Y343YK` — Саныч, тот же адрес 1 — НЕ заблокирован.**

#### ⚠⚠ Блокировка НЕ ЗАПРЕЩАЕТ проезд

Критично для регламента: «Заблокирован» — **метка, а не запрет**.

- пропуск **остаётся виден охране** и не пропадает из списка КПП `[✓ 170]`
- кнопка **«Приехал» активна** — заблокированную машину можно впустить
- кнопка **«Уехал» тоже активна** — машина на территории выезжает без возражений сервера `[✓ 160, 161]`

⇒ Механизм **информирующий**. Охранник, не заметивший красную строку, пропустит машину и ничего не заподозрит. Раздел 25.

#### Регламент для «Радонежского»

> Поля «Минуты» заполнять **только после согласования нормативов с заказчиком и с запасом.** Одна фура, простоявшая на рампе дольше норматива, замораживает пропуска всей компании — включая машины, которые уже в пути.

## 16.5 ⚠ Часовые пояса — критично при удалённом администрировании

**Сервер платформы живёт по московскому времени (UTC+3).** Подтверждено экспериментально `[✓ 55]`: при попытке создать пропуск сервер потребовал «дата начала должна быть после или равной `2026-08-10 00:25:00`» в момент, когда на техасских часах было `16:29` 9 августа. `16:29` UTC−5 = `00:29` по Москве — то есть сервер требует «не раньше чем сейчас», считая по своим часам.

**Форма при этом подставляет время браузера.** Отсюда расхождение: администратор западнее Москвы не может создать пропуск «на сейчас» — система считает это прошлым.

**Один и тот же пропуск на трёх экранах показывает три разных времени** `[✓ 65, 66, 74]`:
| Экран | Значение |
|---|---|
| форма при вводе | 9:40 |
| список пропусков | 20:40 |
| страница приглашения | 12:40 |
| история событий в карточке | по Москве |

**Практические следствия:**
1. **Челябинск (UTC+5) впереди Москвы** — местная охрана в эту стену не упрётся, для неё «сейчас» всегда в будущем относительно сервера. Проблема только у администратора западнее Москвы.
2. **Администратору из другого пояса: переставить часовой пояс на рабочей машине на `UTC+5, Екатеринбург`.** Тогда видишь ровно то же, что охрана на объекте, и методичка пишется в их системе координат.
3. ✅ **Настройки пояса объекта НЕТ** — вкладка ИНФОРМАЦИЯ снята, там только реквизиты `[✓ 148]`. Задать пояс негде.
4. ⚠ **Внутри одной карточки уживаются два пояса** `[✓ 139]`. В карточке запроса поле **«Дата создания» идёт по времени браузера администратора**, а «Дата начала пропуска», «Дата окончания» и «Когда» в блоке решения — по серверному. Запрос № 4: создан в `06:24` по карточке, при этом на телефоне арендатора в момент отправки было `14:24`. Местный администратор увидит там другое число, чем удалённый.
5. **Рабочие экраны (список пропусков, карточка пропуска, история событий, блок ПРИНЯТО РЕШЕНИЕ) идут по московскому времени.** Расхождение из-за браузера касается формы создания и поля «Дата создания» в запросе.
4. **До обучения обязательно** пересмотреть все экраны из русского пояса: расходятся ли они между собой для местного пользователя или только для западного.

### 22.2 Ключевая бизнес-логика для реализации
- Нормализация ГРЗ: кириллица→латиница, uppercase, убрать пробелы. Хранить в `plate_normalized` и искать по ней. **В оригинале это реализовано** (подтверждено надписью в форме чёрного списка), но валидация маски по умолчанию выключена — стоит включать по умолчанию.
- **Трёхзначный режим прав** `allow / deny / on_request` вместо булева флага — сильное решение оригинала. Один и тот же продукт закрывает и ЖК с самообслуживанием, и режимный объект с согласованием каждого заезда, без форков.
- **Приоритет по минимальной цене** при пересечении тарифных правил — избавляет от явного веса правил, но контринтуитивен: более специфичное правило не обязательно выигрывает. Явный `priority` понятнее.
- Лимит времени на территории в минутах, привязанный к опции (разгрузка = 90 мин) — простая и полезная механика для логистики.
- Автоподстановка `ends_at = now() + object.max_duration[pass_type]` при смене типа.
- Переход `inside → (single ? closed : outside)` — единственная нетривиальная ветка автомата.
- Cron: `expired` по истечении `ends_at`; удаление через 30 дней после `closed_at`.
- Аудит: каждое изменение статуса пишется в `pass_events` с актором (сотрудник / пользователь / робот / интеграция).
- Мультиобъектность: один оператор — много объектов; настройки резолвятся через адрес.

### 22.3 Что стоит сделать лучше оригинала
- Не терять список при поиске (показывать «фильтр активен» с крестиком).
- Марку искать без учёта раскладки и регистра.
- Отчёт об ошибках импорта построчно, а не «всё или ничего».
- Явная настройка «требовать согласование» для любого типа пропуска.
- Единая терминология: разовый ≠ одноразовый ≠ разовые.
- **Валидацию делать на вводе и не врать в уведомлении.** Оригинал принимает отрицательный вес сортировки, показывает его в поле, рапортует «успешно сохранено» и записывает дефолт `[✓ 35, 36]`. Либо не давать ввести, либо сказать, что значение изменено, — но не молча.
- **Не допускать дублей порядкового веса** в справочниках без предупреждения, либо задать детерминированный tie-break и показать его пользователю.
- Справочники (типы транспорта и пр.) — уровня аккаунта с возможностью переопределить на объекте, а не копипаст под каждый объект.
- При удалении элемента справочника показывать, сколько сущностей на него ссылается, и что с ними станет.
- **Сообщение об ошибке должно называть причину.** Бэкенд вендора умеет отдавать нормальную диагностику — на публичном API видно `{"detail":[{"type":"less_than_equal","loc":["query","per_page"],"msg":"Input should be less than or equal to 100"}]}`. А в админке то же самое приложение выдаёт «Выбранный тип пропуска запрещён» без указания настройки. Диагностика есть, её просто не показывают.
- **Одно время на всех экранах.** Оригинал показывает один пропуск в трёх разных поясах на трёх экранах (см. 16.5). Хранить в UTC, отображать в поясе объекта, подписывать пояс явно.
- **Не прятать управляющий элемент, когда он недоступен — показывать его задизейбленным с причиной.** Исчезнувший селектор типа пропуска стоил полудня диагностики; надпись «недоступно: не задан максимальный срок» решила бы вопрос за секунду.
- **Разделять «право открыть форму» и «право сохранить».** Если сохранение заведомо запрещено — не давать открывать форму.

## 25. Вопросы и замечания вендору (накопительно)

Копится по ходу работы, отправляется **пачкой**, а не по одному. **26 пунктов на 11.08.2026**, из них 5 блокирующих. Канал: чат поддержки в правом нижнем углу админки. Обращение согласовать с «Интеграцией» — вендор увидит его как обращение клиента.

### Блокирующее

**1. Редактирование пропуска молча меняет тип транспорта на «Легковой».**
Форма «Редактирование пропуска» подставляет в поле типа транспорта дефолт `Легковой` вместо сохранённого значения и записывает его при сохранении. Воспроизведено дважды, независимо:
- `E555EE`, было **Спецтехника**, правил охранник, менялся только комментарий → стало **Легковой** `[✓ 142]`. Цепочка от источника: приложение арендатора `[✓ 138]` → карточка запроса `[✓ 139]` → список до правки → список после `[✓ 142]`.
- `T111TT`, было **Фура**, правил администратор, менялся только комментарий → стало **Легковой** `[✓ 145]`.

**Почему важно:** тип транспорта — ключ фильтрации КПП. Испорченный пропуск перестаёт отображаться на посту, где этот тип перечислен, при этом остаётся валидным и видимым администратору. Охрана разворачивает машину с исправным пропуском. При создании пропуска подмены нет `[✓ 151]` — только при редактировании.

**2. Рабочей настройки прав охраны не существует.**
`Редактирование = Только статус` **не работает**: сотрудник группы «Охрана (КПП)» открывает форму и меняет все поля — адрес, пользователя, тип пропуска, даты, тип гостя, ФИО, комментарий — и успешно сохраняет `[✓ 110, 111, 142, 143]`.
`Редактирование = Запрещён` гасит **и кнопку «Приехал»** `[✓ 146]` — охранник не может отметить въезд, пост встаёт целиком.
**Почему важно:** либо охрана бесконтрольна и может задним числом легализовать проезд, которого не было, либо она не может работать. Третьего варианта нет, а на это право рассчитан весь регламент поста. **Блокирует сдачу объекта в эксплуатацию.**

**3. Пропуск невозможно отредактировать после наступления времени начала.**
Сервер требует «дата начала ≥ текущего времени» при каждом сохранении, а не только при создании: «Дата в поле Дата начала должна быть после или равной 2026-08-11 14:12:00» `[✓ 136]`. При этом первое поле даты в форме редактирования недоступно для правки — выполнить требование нечем.
**Почему важно:** опечатку в ГРЗ у машины, стоящей на воротах, исправить нельзя; продлить срок нельзя. Только перевыпуск пропуска.

**4. Пешеходные пропуска не видны на КПП, где указан хотя бы один тип транспорта.**
`[✓ 107, 108, 109]` У пешеходного пропуска типа транспорта нет, фильтр строится по пересечению — пропуск отсекается. Перечисление всех типов не помогает.
**Почему важно:** курьеры, рабочие подрядчиков и проверяющие для поста невидимы; охрана разворачивает людей с корректно оформленными пропусками.

**5. Несколько КПП у одного сотрудника дают пересечение, а не объединение.**
Сотрудник, привязанный к КПП с адресами и к КПП с типами транспорта, видит **ноль** пропусков.
**Вопрос:** так задумано? Ожидаемое поведение — объединение: добавляя пост, администратор рассчитывает, что охранник увидит больше, а не меньше.

**6. Как штатно настроить пост, где проходят и пешеходы, и транспорт определённых типов?**
Наше решение — две учётные записи в двух браузерах на одном посту. Есть ли предусмотренный способ?

### Ошибки и неточности

**7. Сообщение «Выбранный тип пропуска запрещён» не указывает причину.**
Причин две и они независимы: нулевые максимальные сроки пропусков и `Запретить` в правах сотрудников. Диагностика на разбор ушло несколько часов.
Показательно: публичный API того же вендора отдаёт точную ошибку — `{"detail":[{"type":"less_than_equal","loc":["query","per_page"],"msg":"Input should be less than or equal to 100"}]}` `[✓ 59]`. В админке это не выводится.

**8. Молчаливая подмена значения при сохранении.**
Поле «Сортировка в списках» принимает отрицательное значение, показывает его, отдаёт тост «успешно сохранено» — а записывает `10` `[✓ 35, 36]`.

**9. Разные экраны показывают время одного пропуска в разных часовых поясах** `[✓ 65, 66, 74]`: форма ввода `9:40`, список пропусков `20:40`, страница приглашения `12:40`, история событий — по Москве. Внутри одной карточки запроса тоже два пояса: «Дата создания» идёт по времени браузера, остальные поля по серверному `[✓ 139]`.
**Настройки часового пояса объекта в продукте нет** — вкладка ИНФОРМАЦИЯ содержит только реквизиты `[✓ 148]`. Как удалённому администратору видеть то же, что охрана на объекте?

**10. В карточке РАЗОВОГО запроса не показан конец срока действия.**
Поле одно — «Дата пропуска», и в нём начало `[✓ 130]`. У временного запроса полей два `[✓ 139]`. Данные о конце в запросе есть: после одобрения пропуск получает корректный период. Администратор одобряет заезд, не видя, до которого часа выдаёт доступ.

**11. Переименование адреса переписывает историю задним числом.**
Пять ранее созданных пропусков немедленно сменили отображаемый адрес `[✓ 154, 155 против 132]`. При смене арендатора бокса весь прошлый журнал заездов обезличивается. Предусмотрен ли способ сохранить историческое имя?

**12. Удаление КПП и типа транспорта происходит без диалога подтверждения** `[✓ 34, проверено 11.08.2026]`.

**13. Документация расходится с продуктом.**
- База знаний `support.pass24pro.ru` утверждает, что при создании пользователя приходит SMS-приглашение. **Не приходит** (проверено на живом номере).
- Там же: при блокировке адреса «существующие пропуска останутся активными». Подсказка в интерфейсе говорит обратное: «не могут заказывать **и использовать**».
- Там же описаны три режима одобрения (авто/ручное/смешанное). В продукте — четыре независимых сочетания со значениями Разрешить/Запретить/По запросу.
- Обещаны четыре предустановленные роли — на объекте существует только «Администраторы».

**14. Кнопка «ДОБАВИТЬ ГОСТЯ» молча теряет данные второй машины.**
Форма принимает вторую строку транспорта, отдаёт «Пропуск успешно сохранён» — и не создаёт ничего `[✓ 166, 167, 168]`. Ни второй карточкой, ни строкой в первой. Проверено на трёх экранах, включая оба КПП. Либо функция должна работать, либо кнопку нужно убрать.

**15. Метка «Заблокирован» не запрещает проезд.**
При блокировке по превышению времени пропуск остаётся виден охране, кнопки «Приехал» и «Уехал» активны, сервер не возражает `[✓ 160, 161, 170]`. Механизм информирующий, а не запрещающий. **Вопрос:** есть ли режим, в котором блокировка действительно запрещает въезд?

**16. Нет контроля вместимости территории.**
Требование заказчика: не более N машин одного арендатора одновременно на территории. Лимит активных пропусков считается по пользователю и ограничивает **создание** пропуска, а не въезд `[✓ 158, 165]`. Предусмотрен ли механизм по фактическому числу машин внутри?

**17. Как штатно исправить ошибку арендатора в заявке?**
В карточке запроса полей для правки нет `[✓ 129]` — только «Одобрить» или «Отклонить». После одобрения пропуск не редактируется (вопросы 1 и 3). Единственный найденный путь — отклонить и просить переоформить. Есть ли предусмотренный?

**18. Отключается ли блок «Специальные предложения»** в мобильном приложении арендатора `[✓ 116]`? Это рекламная врезка в интерфейсе, который увидят арендаторы заказчика.

**19. Почему ФИО, заведённое администратором, не подтягивается в профиль пользователя?** В приложении вместо имени показано «Не указано» `[✓ 122]`.

### Вопросы по составу поставки и лицензии

**20.** Входит ли **PASS24.guard** в тариф заказчика? Если да — обучать охрану надо ему, а не веб-интерфейсу.
**21.** Чем на КПП сканируют QR: PASS24.admin, guard или веб-сканер (модуль «Сканер QR» есть в правах)?
**22.** Есть ли модуль **«Журнал событий»**? Вендор его описывает, в меню объекта его нет.
**23.** **Иностранные номера.** Официальный перечень допустимых форматов `[✓ 147]` содержит четыре маски, все российские. Казахские и белорусские фуры ни в одну не укладываются. Как их оформлять при включённой настройке «Формат номера автомобилей обязателен»?
**24.** Нужен ли модуль **«Мультиобъект»** и тариф Бизнес, если «Интеграция» будет вести несколько клиентов на одном аккаунте.
**25.** Есть ли **API** и документация к нему.
**26.** Лимиты лицензии по числу объектов, адресов, пользователей.

## 26. Копилка для собственной платформы

Собирается по ходу изучения PASS24. Не действовать по ней сейчас — это материал на будущее.

### Модель доступа и КПП

**Пешеход — это тип участника, а не отсутствие машины.** Вся проблема раздела 3.5 растёт отсюда: фильтр строится по типу транспорта, а у пешехода такого поля нет. Правильно: фильтр поста = список разрешённых типов транспорта **плюс отдельный чекбокс «пешеходы»**.

**Множественная привязка должна давать объединение.** Пересечение по умолчанию контринтуитивно. Если пересечение нужно — делать явным переключателем «И / ИЛИ» с подписью, что получится.

**Разделить видимость и разрешение — ключевая идея.**
Сейчас пропуск не своего поста просто не показывается, и он неотличим от несуществующего. Правильно: показать его с красной плашкой **«Не ваш пост — направьте на КПП-1»**, кнопку «Приехал» заблокировать, а в журнал записать событие **«попытка въезда не на своём посту»**. Тогда:
- охранник ничего не отметит по ошибке;
- водитель получает внятное направление вместо «пропуска нет»;
- в журнале появляется информация, которая сейчас теряется полностью.

**Новая дочерняя группа прав должна создаваться с минимальными правами**, а не наследовать полный доступ родителя. Наследование «всё разрешено» по умолчанию — это дыра, а не удобство.

**Право «видеть раздел» не должно влиять на выпадающие списки в чужих формах.** Запрет доступа к модулю «Сотрудники» скрывает группы прав при заведении сотрудника — это два разных права, их надо разделить.

**Права обязаны работать.** Настройка, которая молча не применяется, хуже отсутствующей: на неё строят регламент.

**Смена статуса — отдельное право, а не подвид редактирования.** В оригинале `Запрещён` на редактирование гасит и кнопку «Приехал», из-за чего охране нельзя выдать роль «двигает статусы, не трогает содержимое». Это ровно та роль, которая нужна на посту в 100% случаев. Разделять на уровне модели: `pass.edit_content` и `pass.change_status` — разные разрешения.

**Форма редактирования не должна иметь дефолтов.** Дефолт осмыслен только при создании. В форме правки любое поле, не заполненное реальным значением из базы, — это готовая порча данных: оригинал молча меняет тип транспорта на «Легковой» при сохранении любой правки. Правильно: форма правки блокируется до полной загрузки сущности, и отправляется только то, что пользователь изменил (PATCH, а не PUT дефолтами).

**Валидация «не в прошлом» применяется к созданию, а не к правке.** В оригинале требование «дата начала ≥ сейчас» проверяется при каждом сохранении, а поле начала при этом недоступно — сущность запирается навсегда в момент, когда её время наступило. Правильно: проверять только при изменении самого поля.

**Разделять «право открыть форму» и «право сохранить».** Если сохранение заведомо запрещено — не давать открывать форму.

### Ошибки, валидация, обратная связь

**Сообщение об ошибке называет причину.** Не «Выбранный тип пропуска запрещён», а «Максимальный срок одноразового пропуска = 0 ч. Задайте ненулевое значение в настройках объекта».

**Валидация на вводе, а не на сохранении.** Обязательные поля помечать сразу при открытии формы. Правило «хотя бы одно из двух полей» показывать в форме, а не всплывающим текстом после нажатия.

**Никакой молчаливой подмены значений.** Либо не давать ввести, либо явно сказать «значение изменено на X, потому что Y». Тост «успешно сохранено» не должен появляться, если сохранено не то, что ввели.

**Не прятать недоступный управляющий элемент — показывать задизейбленным с причиной.** Исчезнувший селектор типа пропуска стоил полудня; надпись «недоступно: не задан максимальный срок» решила бы вопрос за секунду.

**Нули не должны означать запрет.** `0` в поле «максимальный срок» читается как «без ограничений», а означает «ноль часов». Нужен явный переключатель «без ограничения» + числовое поле.

**Тип сущности выбирается явно, а не выводится из данных.** Тип пропуска в PASS24 определяется длительностью интервала — неочевидно и непредсказуемо. Правильно: пользователь выбирает тип, система проверяет, укладывается ли срок.

### Справочники и данные

**Справочники — уровня аккаунта с возможностью переопределить на объекте**, а не копипаст под каждый объект.

**Переименование сущности не должно переписывать историю.** В оригинале адрес хранится ссылкой, и смена названия задним числом меняет его во всех прошлых пропусках и отчётах. При смене арендатора склада весь прошлый журнал заездов становится ложным. Правильно: в журнальных записях хранить снимок отображаемого имени на момент события, а ссылку — для навигации.

**Фильтры с пустым списком: сформулировать явно.** В оригинале пустой список типов транспорта на КПП означает «не фильтровать», а не «ничего не пропускать» — поведение верное, но нигде не написано, и человек читает пустое поле как «ничего не выбрано». Показывать в интерфейсе прямым текстом: «типы не заданы — пропускаются все».

**Дубли порядкового веса** — предупреждать или задать детерминированный tie-break и показать его пользователю.

**При удалении элемента справочника** показывать, сколько сущностей на него ссылается и что с ними станет.

**Единая терминология.** «Разовый» / «Одноразовый» / «Разовые» в одном продукте — три написания одной сущности. Один термин везде, включая настройки и фильтры.

**Не подставлять молча первое значение справочника.** Тип автомобиля по умолчанию «Легковой» на логистическом центре гарантирует мусор в отчётности. Либо пусто с обязательным выбором, либо дефолт настраивается администратором объекта.

**Импорт лежит там, где сущность.** Импорт пользователей в PASS24 находится в разделе «Адреса» — вендор сам это проговаривает в обучающем видео как особенность.

### Время

**Хранить в UTC, отображать в часовом поясе объекта, подписывать пояс явно.** Оригинал показывает один пропуск в трёх поясах на трёх экранах.

**Время объекта — свойство объекта**, а не браузера администратора. Удалённый администратор должен видеть то же, что охрана на посту.

### Согласование

**В карточке заявки показывать всё, что будет создано.** Оригинал в карточке разового запроса выводит только начало срока, а конец — нет, хотя он в заявке есть. Администратор одобряет доступ, не зная его длительности. Правило: карточка решения показывает полный набор полей будущей сущности.

**Дать возможность править заявку при одобрении.** Отклонить из-за одной опечатки в типе транспорта и ждать переоформления — дорого. Правильно: «Одобрить с изменениями», с записью в аудит, что именно поменял согласующий.

### Интерфейс охраны

**Хорошее, что стоит перенять:**
- комментарий к пропуску и иконки опций видны прямо в списке, без открытия карточки;
- история событий с автором и временем по каждому действию;
- фильтр «на территории» + тип гостя = мгновенный ответ «сколько машин сейчас внутри»;
- проверка номера по чёрному списку в реальном времени при вводе.

**Что доделать:**
- посимвольный запрос на проверку номера — добавить дебаунс, сейчас запрос на каждую букву `[✓ 64]`;
- массовые режимы не прятать за иконкой без подписи (красный замок = «массовое закрытие»);
- отчёт отдавать скачиванием в интерфейсе, а не только письмом со сроком жизни 24 часа;
- ограничение «31 день на один отчёт» — произвольное, снять или объяснить.

### Внешние страницы

**Страница приглашения** (`invite.*`) открывается без авторизации: у кого ссылка — у того доступ. Нужен одноразовый токен и срок жизни.
**И там же не хватает главного для водителя:** физического адреса объекта, схемы проезда, номера нужного КПП, телефона поста. Сейчас это только пропуск, а не навигация.

### Контур арендатора

**Веб-кабинет для арендатора обязателен.** В PASS24 арендатор существует только на телефоне. Реальный сценарий: логист сидит за компьютером, заявка от перевозчика приходит письмом с номерами машин и ФИО — а он должен глазами переписать это в телефон. При потоке в десятки машин в день это откровенно плохо. Нужен веб-кабинет, где работает копипаст.

**Массовый ввод у арендатора.** В мобильном есть «Из шаблона», но нет ни поля «вставить список», ни загрузки файла. Перепечатывать приходится по одному пропуску. Арендатору с колонной из десяти машин нужен способ загрузить их разом.

**Заведение пользователя администратором должно сразу создавать рабочую учётку** — с приглашением по SMS или ссылкой на установку. В оригинале запись без пароля неотличима от рабочей: администратор видит пользователя в списке и думает, что тот может входить, а тот не может.

**Никакой рекламы в интерфейсе, который видит клиент клиента.** Блок «Специальные предложения» в приложении арендатора — врезка вендора в рабочий инструмент заказчика.

**Дефолты одинаковые во всех контурах.** Тип транспорта предзаполнен «Легковым» в вебе и в приложении, но пуст на странице приглашения.

**Согласование должно масштабироваться.** Режим «одобрять каждый заезд» при потоке в сотню машин нерабочий. Нужны правила автоодобрения: доверенный арендатор, повторяющийся номер, рабочее время — с ручным разбором только исключений.

### Учётные записи

**Email сотрудника не верифицируется** — принят `test@test.com`. Без реального адреса не работает восстановление пароля.
**Пароль сотрудника задаёт администратор и передаёт лично.** Нужен механизм обязательной смены пароля при первом входе.
