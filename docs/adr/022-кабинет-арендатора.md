# ADR-022. Кабинет арендатора: пропуска (этап 7a)

Статус: принято (13.10.2026, этап 7a). Дополняет ADR-017 (API ядра), ADR-020 (UI и мастер), ADR-021 (админка 6b); закрывает Q-75, фиксирует решения Q-76–Q-80.

## Контекст

Логист арендатора должен без инструкции оформлять пропуска — по одному и пачкой из Excel — и до сохранения видеть, пустят ли машину и почему (`08_`, `16_` C). Админка (6a, 6b) уже даёт всё для настройки объекта; API пропусков, пакета, согласования и подсказок есть с этапов 4–5, но у арендатора не было экранов, у согласующего — очереди, а движок не знал, что номер из чёрного списка опасен и без пропуска (вопрос из 6b.1).

## Решение

### 1. Чёрный список без пропуска — в движке, чистой функцией

`findBlacklisted(entries, {plateNorm | personName}, now)` (`packages/engine/src/blacklist.ts`): действующая запись по номеру или имени (без учёта регистра), время — параметром. `evaluate` использует её в двух местах: проверка 3 для найденного пропуска (как раньше) и ветка «пропуска нет» (`plate` без пропуска или с несколькими арендаторами; `pedestrian_lookup`) — красный `deny` «В чёрном списке: причина», `primaryAction: refuse`, без `request_pass`, `override_request`, `choose_tenant`. На выезде — прежний `no_pass` с отметкой и строкой-предупреждением (Q-10). Следствия: песочница «как на посту» и пост (этап 8) получают красный сами, через общий `evaluate`; `POST /gate/requests` для номера из списка отвечает 403 (арендатору такой запрос не уходит); `ENGINE_VERSION` 0.4.0. Та же функция даёт предупреждение в форме пропуска.

### 2. Форма пропуска: подсказки по POST, предупреждения — `notices`

`GET /tenants/:id/pass-hints` остаётся, но номер и имя — персональные данные: в адресе запроса они попадали бы в журналы, поэтому форма использует `POST /tenants/:id/pass-hints` (то же тело + `plate`, `personName`). В ответ добавлено `notices[]`: `tenant_blocked` и `contract_expired` (`error` — кнопка неактивна, под ней причина), `tenant_entry_blocked` и `blacklisted` (`warning`). Причину записи чёрного списка видит только не-арендатор; пользователю арендатора — «в чёрном списке, подробности у администратора объекта». Пропуск на такой номер **оформляется** с предупреждением (`warnings[].code = blacklisted` в ответе создания и в строках пакета) — на въезде он всё равно красный (Q-76).

### 3. Один запрос — всё для шапки и форм

`GET /tenants/:id/cabinet` (права `pass.view` | `pass.view_all_tenants`): арендатор, объект с поясом и подписью («Челябинск, UTC+5»), включённые типы транспорта с признаком «доступен арендатору» (тот же `availableCategories`, что у подсказок), зоны, цели визита, доки арендатора, «сегодня» и «сейчас» сервера. Тот же ответ нужен согласующему (карточка очереди) — читать каталоги без `site.manage` ему не нужно. Время «сейчас» формы берётся по часам сервера (сдвиг к часам браузера по ответу), чтобы допуск «начало в прошлом» (Q-58) не срабатывал от расхождения часов.

### 4. Кабинет — `/cabinet/*`, отдельно от `/admin`

Оболочка: компания и объект с поясом в шапке, переключатель компании по назначениям ролей на арендатора (выбор помнится), меню только из доступного по правам, на телефоне — нижнее меню с кнопками ≥ 64 px. Люди, у которых все назначения — на арендатора, с `/` попадают в кабинет. Данные — тот же `useApi` с ключом `['data', путь]`; обновление без F5 — `useSiteEvents`: доменные события объекта (SSE, ADR-004; `payload` без ПДн, арендатору приходят только события его компаний) сбрасывают кэш `['data']` и подсказки с задержкой 250 мс (пачка в 20 пропусков — одно обновление). Админка подписывается так же (очередь согласования и бейдж), если у человека есть право читать события.

### 5. Пакет: разбор в вебе, судья — сервер

Колонки: Номер · Тип · Марка · Водитель · Окно · Комментарий · Док; разделители Tab, `;`, запятая; заголовок определяется. Типы транспорта и доки сопоставляются со справочниками арендатора (без регистра, однозначное сокращение допустимо), окно — «12:00-14:00», «с 12 до 14», с датой. Тип пропуска и срок — общие для пачки (с общим комментарием для многоразовых). Строка → тело `POST /passes/batch` теми же `buildPassBody`, что и форма (одно место для часовых поясов). Предпросмотр идёт сам (`useAutoPreview<PassBatchResult>`, `dryRun`), «сейчас» фиксируется при смене ввода, чтобы проверка не перезапускалась сама, и берётся заново при сохранении. Итог — «Создано N из M, K с ошибками» со строками (номер строки, номер, причина); строки с ошибками остаются в поле для исправления.

### 6. Автопарк и «повторить вчерашний день»

Автопарк — таблица `fleet_vehicles` (была в схеме) как ресурс `fleet` на общей фабрике справочников: `GET/POST /tenants/:id/fleet`, `PATCH/DELETE /fleet/:id` (мягкое удаление с показом использований), пакет `POST /tenants/:id/fleet/batch` (`dryRun`). Читают `pass.view`/`pass.view_all_tenants`, правит новое право **`fleet.manage`** (шаблон «Арендатор — ответственный»; владелец и администратор объекта — автоматически); миграция `0009_fleet_role_templates_sync` добирает право ролям по шаблонам (ADR-007 «Новое право»). «Повторить день» — `POST /tenants/:id/passes/repeat {sourceDate, targetDate, dryRun}`: разовые пропуска, начинавшиеся в исходный местный день, пересоздаются на целевой день теми же часами (`localInstant`, поясом объекта) через общий `createBatch` — проверки, дубли, согласование и предпросмотр те же, что у пакета.

### 7. Очередь согласований в админке

`/admin/approvals` (право `pass.approve`): карточка со всеми полями будущего пропуска, кто и откуда заказал; «Одобрить», «Отклонить…» (причина обязательна, её видит арендатор), «Одобрить с изменениями…» — форма правки (`useEditForm`: без значений по умолчанию, отправляются только изменённые поля) с комментарием согласующего. Арендатор видит в статусе «Одобрено с изменениями» и «было → стало» по полям, «Отклонено: причина».

### 8. Проверка: E2E продолжает базу

Файл `e2e/cabinet.spec.ts` — отдельный проект Playwright `cabinet`, зависящий от `chromium`: он идёт после `clean-start.spec.ts` на той же чистой базе (мастер, организация, объект, арендаторы уже есть). Без зависимости файлы шли бы параллельно, а «чистый старт» отказывает на непустой базе.

## Альтернативы

- **Номер и имя подсказки в query-строке GET**: проще, но ПДн в журналах доступа и в истории браузера (CLAUDE.md: ПДн не пишутся в логи).
- **Запретить оформление пропуска на номер из чёрного списка**: честнее по смыслу, но выдаёт арендатору больше (точное «этот номер нельзя»), а решение «блок или предупреждение» принимает заказчик (Q-76); сейчас — предупреждение по постановке этапа.
- **Отдельный список справочников для кабинета (категории, зоны, доки — тремя запросами)**: ответы `site.manage`-ресурсов арендатору недоступны или избыточны; один `cabinet` проще и согласованнее с подсказками.
- **Автопарк отдельной таблицей-«шаблоном»**: таблица `fleet_vehicles` уже в схеме (`DATA_MODEL`, 11_); дублировать нечем.
- **Повтор дня на клиенте (список → пакет)**: сдвиг часов через часовой пояс браузера — прямое нарушение ADR-009; на сервере сдвиг идёт поясом объекта.
- **Общий `react-hook-form` в форме пропуска**: форма зависит от серверных подсказок и пересчитывает тело (время объекта) на каждом шаге; обычное состояние проще, а ошибки приходят и от клиентской проверки, и от сервера по `field`.
