# ADR-008. Интеграция оборудования: контракты, агент КПП, адаптеры, симуляторы

Статус: принято. Реализация драйверов — после MVP; контракты, таблицы, симуляторы — в MVP (`16_` D).

## Контекст

Камеры номеров, реле шлагбаумов, QR-сканеры и СКУД стоят в локальной сети поста; сервер — в облаке и до них не достучится. Марки неизвестны. Ядро и экран поста не должны знать протоколов. Шлагбаум открывается только по зелёному вердикту; при отсутствии ответа охранник открывает вручную.

## Решение

### Контракты (`packages/hardware`, zod)

```ts
// Вверх: агент → сервер
type HardwareEvent =
  | { type:'plate_recognized'; gateId; deviceId; direction:'in'|'out'; plateRaw; confidence: number; photoRef?; at: Instant; seq: number }
  | { type:'qr_scanned';       gateId; deviceId; payload: string; at; seq }
  | { type:'barrier_state';    gateId; deviceId; state:'open'|'closed'|'fault'; at; seq }
  | { type:'acs_pass';         gateId; deviceId; cardId; direction; at; seq }
  | { type:'heartbeat';        deviceId; at; seq; status: Record<string, unknown> };

// Вниз: сервер → агент
type HardwareCommand =
  | { type:'open';  commandId; gateId; deviceId; direction; cause:'check_in'|'check_out'|'override'|'auto_pass'|'manual_test'; timeoutMs: number }
  | { type:'close'; commandId; gateId; deviceId }
  | { type:'test';  commandId; deviceId };

type CommandResult = { commandId; status:'done'|'failed'|'timeout'; at; detail?: string };

// Интерфейсы адаптеров внутри агента
interface CameraAdapter  { start(emit: (e: HardwareEvent) => void): Promise<void>; stop(): Promise<void> }
interface BarrierAdapter { open(direction): Promise<CommandResult>; close?(): Promise<CommandResult>; health(): Promise<'ok'|'fault'> }
interface ScannerAdapter { start(emit): Promise<void> }
interface AcsAdapter     { syncPasses(passes: PedestrianPassView[]): Promise<void>; start(emit): Promise<void> }
```

### Транспорт агент ↔ сервер

- Агент — устройство учётки КПП (`gate_devices.kind = 'agent'`), привязывается тем же кодом из админки (агент на сервере обслуживает несколько КПП — по одному устройству-привязке на КПП в его конфиге), держит **исходящие** соединения: `POST /agent/events` (батчи, `(deviceId, seq)` — идемпотентность) и `GET /agent/events` SSE для команд (ADR-004). Результат команды — `POST /agent/commands/{id}/result`.
- Нет связи с сервером — агент буферизует события на диске (SQLite-файл или JSONL, до 10 тыс.), команды не приходят — охранник открывает вручную; экран поста показывает «агент не на связи».
- Сервер ждёт результат `open` не дольше `timeoutMs` (по умолчанию 5 с); иначе `barrier_commands.status = 'timeout'` и событие `barrier.result` → «Шлагбаум не ответил — откройте вручную».

### Агент КПП (`apps/gate-agent`)

Node 22-процесс. **В режиме «на объекте» (ADR-011) агент — сервис `gate-agent` в том же compose на сервере объекта** (профиль `agent`): камеры и реле стоят в той же LAN, отдельное железо не нужно, и агент получает те же бэкапы, обновления и мониторинг. Отдельный экземпляр на ПК поста или мини-ПК (Windows-служба через NSSM, Linux — systemd) — только когда сегмент КПП изолирован от сервера или объект в режиме «облако». Один КПП обслуживается ровно одним агентом; агентов у объекта может быть несколько. Конфиг `agent.yaml`: токен, список устройств `{id, kind, adapter, options}`. Адаптеры — модули в `apps/gate-agent/src/adapters/<vendor>/`; загружаются по имени. Секреты камер (логины) — только в конфиге агента, в БД — нет.

### Как ядро использует события

1. `plate_recognized` → `hardware_events` → нормализация (`@oxrana/plates`) → кандидаты (точное + нечёткое совпадение) → `engine.evaluate` → `gate_decisions(action: none)` → SSE `lpr.candidate` на пост с фото и вердиктом; карточка открывается сама.
2. При `gate.auto_pass_on_allow` и выполнении **всех** условий (точное совпадение одного пропуска, `confidence ≥ plateFuzzyThreshold`, вердикт `allow` без `warn`, направление однозначно) — `checkIn(method:'auto')` и команда `open`. Любое сомнение — ждём кнопку.
3. Команда `open` создаётся только внутри транзакции `checkIn`/`checkOut`/override (ADR-006). Иных путей нет; `manual_test` — только из реестра устройств правом `hardware.manage`.
4. `qr_scanned` с USB-сканера (эмулирует клавиатуру) обрабатывается в PWA поста локально: токен → `GET /gate/passes/by-token` → карточка. Через агент идёт только сетевой сканер.
5. `acs_pass` (СКУД) — проход на внутреннем посту (`gate_passages`); синхронизация пеших пропусков в СКУД — задача pg-boss, адаптер `AcsAdapter`.

### Реестр устройств и симуляторы

- Админка → Объект → Оборудование: список `hardware_devices` со статусом (по `heartbeat`, таймаут 90 с), кнопка «Проверить: открыть шлагбаум», журнал команд и событий, фото по ссылке со сроком.
- Симуляторы — адаптеры `sim-camera` и `sim-barrier` в `packages/hardware/src/sim/`: камера эмитит номер по HTTP `POST /sim/plate` или из сценария, шлагбаум отвечает `done`/`failed`/`timeout` по настройке. Используются в E2E (Playwright поднимает агент с симуляторами) и в режиме «демо» в админке.
- Фото: хранилище по ключу (`photoRef`): в MVP — диск сервера `data/photos/<site>/<yyyy-mm>/`, выдача через подписанную ссылку; срок — `retentionDays.photos`. Переход на S3-совместимое хранилище в РФ — смена реализации `FileStore`.

## Альтернативы

- **MQTT-брокер** между агентом и сервером: ещё один сервис и порт; SSE + POST дают то же на одном HTTPS.
- **Сервер напрямую ходит к камерам** (ISAPI/ONVIF): требует белого IP или VPN на каждом КПП; не работает при падении канала.
- **Облако вендора камер** (как PASS24.auto): привязка к марке, события через третью сторону.
- **Агент на Python/Go**: второй стек; у нас Node уже есть и контракты общие в TS.

## Последствия

- В MVP есть всё, чтобы E2E-тест «камера распознала → карточка открылась → Впустить → шлагбаум открылся» проходил на симуляторах. Реальный драйвер = один модуль адаптера + полевые испытания.
- `visits.method` и ссылки на события/команды заполняются с первого дня (кнопкой — `button`), поэтому отчёты по способу отметки работают сразу.
