# ADR-019. Тестовый стенд на VPS (этап 5b)

Статус: принято (12.10.2026). Первая, упрощённая часть этапа 12: режим «облако» из ADR-011 без WireGuard, мониторинга и S3. Реализует ADR-011 §1 (дистрибутив), §6 (`oxranactl`, обновление и откат), §5 (копии) в минимальном виде; чистый старт — ADR-016, ADR-018 п. 8.

## Контекст

Заказчик должен сам кликать интерфейс и вводить данные настоящего объекта, не дожидаясь этапа 12 и сервера в ЛЦ. Нужен стенд на арендованном VPS (Ubuntu 24.04, 2 vCPU / 4 ГБ, РФ), который сам обновляется при каждом слиянии в `main`, откатывается одной кнопкой и настраивается человеком без навыков программиста. Сделанное не должно выбрасываться: Dockerfile, `compose.yml`, `oxranactl` и скрипты проверки переходят в дистрибутив «на объекте».

## Решение

### 1. Один домен, три пути

`https://<домен>/` — кабинет, `/gate/` — пост, `/api/` — API (Caddy срезает префикс `/api`). Для заказчика это **одна A-запись** и один сертификат Let's Encrypt (HTTP-01, порт 80). Веб и пост и так ходят в API по `/api` на своём адресе (ADR-018 п. 2), так что API не менялся: `PUBLIC_URL=https://<домен>`, `GATE_URL=https://<домен>/gate`; проверка Origin сравнивает origin, а он один. Пост собирается с `GATE_BASE=/gate/` (Vite `base` и `basepath` маршрутизатора из `import.meta.env.BASE_URL`); в разработке и E2E — как раньше, в корне своего порта.

Цена: кабинет и пост — **один origin**, то есть одна база IndexedDB и общий `localStorage`; уязвимость XSS в кабинете дотянулась бы до токена устройства поста. Для стенда приемлемо. **Решение заказчика (12.10.2026, Q-61):** на стенде пост остаётся на `/gate/`; на этапе 8, **до привязки настоящих устройств**, пост выносится на отдельный origin (поддомен) — `GATE_URL` и второй блок в Caddyfile, две строки; устройства привязываются заново. Задача записана в ROADMAP этапа 8.

### 2. Образы и доставка: по SSH, без реестра

Один `deploy/Dockerfile`, две цели: `api` (Node 22, `dist/server.js`, `dist/migrate.js`, `dist/bootstrap.js`, миграции SQL, непривилегированный пользователь, `HEALTHCHECK` по `/readyz`) и `proxy` (Caddy 2 со статикой `web` и `gate` и `Caddyfile`). Версия образов — тег `ГГГГММДД-хэш7`; она же `APP_VERSION` в `/healthz`, по ней проверка после деплоя отличает новую версию от старой.

Доставка: GitHub Actions собирает образы, `docker save | gzip | ssh deploy@сервер oxranactl load`, затем `oxranactl update ТЕГ`. Секретов три (`STAND_HOST`, `STAND_SSH_KEY`, `STAND_KNOWN_HOSTS`) и одна переменная (`STAND_DOMAIN`); ключ сервера закреплён (`StrictHostKeyChecking yes` по `known_hosts` из секрета), без `ssh-keyscan` на лету. Реестру образов (GHCR) пришлось бы выдавать серверу токен чтения или делать пакет публичным, и ещё один секрет обновлять по сроку; приватный реестр РФ — решение этапа 12 (Q-44).

Деплой запускается по завершении CI на `main` (`workflow_run`, только `success` и только если коммит — всё ещё голова `main`) и вручную (`workflow_dispatch`: выкатить / откатить). Пока секретов нет, запуск после CI пропускается с пометкой, а не падает. Очередь деплоев одна, без отмены.

### 3. Обновление, проверка, откат — `oxranactl`

`oxranactl update ТЕГ` (ADR-011 §6): образы есть → PostgreSQL → роли и база (идемпотентно, как `scripts/db-up.sh`) → копия `pre-update` → миграции под владельцем схемы (`dist/migrate.js`) → запись версии → `up -d` → **проверка**: контейнер api healthy, затем `https://<домен>/api/healthz` отвечает **нужной версией** и `/readyz` отвечает — через настоящий Caddy и TLS. Не прошла — версия возвращается на прежнюю автоматически, команда завершается ошибкой (запуск в Actions красный), в вывод попадают последние строки журнала. Миграции откату не подлежат и совместимы на одну версию назад (ADR-003), поэтому прежний образ работает на новой схеме; данные вернёт `oxranactl restore` из копии `pre-update`. Повторное обновление до той же версии ничего не делает (идемпотентно, предыдущая версия не затирается, копий не плодит). Откат — `oxranactl rollback [ТЕГ]` (по умолчанию на предыдущую; повтор возвращает обратно) или кнопка «Run workflow → rollback». Хранятся образы текущей, предыдущей и ещё трёх свежих версий.

Состояние — два файла в `/opt/oxrana`: `.env` (домен и пароли, создаёт `setup-vps.sh`, права 600) и `state.env` (версии, пишет только `oxranactl`). Все операции под `flock`.

### 4. Первичная настройка сервера — `deploy/setup-vps.sh`

Одна команда в веб-консоли хостера: `curl … | bash -s -- ДОМЕН E-MAIL`. Делает: пользователь `deploy` (без `sudo`, в группе `docker`), Docker CE (если репозиторий Docker недоступен — пакеты Ubuntu), брандмауэр `ufw` (22, 80, 443), SSH: вход по паролю выключен файлом `00-oxrana.conf` (имя нарочно первое по алфавиту: в `sshd` побеждает первое значение, а cloud-init кладёт свой файл с `PasswordAuthentication yes`), root — только по ключу; `fail2ban`; `unattended-upgrades` с ночной перезагрузкой при необходимости; swap 2 ГБ; пояс UTC; ключ деплоя (ed25519, в `authorized_keys` с `restrict`); ночная копия базы (systemd-таймер). Идемпотентен: повтор сохраняет пароли и ключ, заново печатает данные для GitHub. Что внутри `docker`-группы — то же, что root на сервере: доступ к серверу = владение ключом деплоя; ограничить ключ принудительной командой — задача этапа 12.

Журнал доступа Caddy пишется без cookie, заголовка `Authorization` и строки запроса (в ней бывают номера и телефоны из поиска): ПДн в журналах быть не должно (CLAUDE.md).

Docker публикует порты в обход `ufw`; в `compose.yml` наружу выставлены только 80 и 443 прокси. PostgreSQL и API — только во внутренней сети.

### 5. Чистый старт

`oxranactl bootstrap` на сервере (вопросы по шагам или параметры) запускает `dist/bootstrap.js` в одноразовом контейнере под владельцем схемы и печатает ссылку установки пароля **в этот терминал**. Из GitHub Actions чистый старт не вызывается никогда, поэтому ссылка не попадает в их журналы; контейнер удаляется (`--rm`), его журнал вместе с ним. Новая ссылка — `oxranactl bootstrap --new-owner-link --owner-email …`.

### 6. Копии

`oxranactl backup`: `pg_dump -Fc` внутри контейнера PostgreSQL, проверка `pg_restore --list`, права 600, каталог `/opt/oxrana/backups`. Ночная (02:00 UTC) — хранится 7; перед обновлением и перед восстановлением — по 3 отдельно (частые деплои не вытесняют ночные). **Только на самом сервере**: потеря диска = потеря копий; копии вне площадки (restic, S3) — этап 12.

### 7. Что вырастет в этап 12

| Стенд (5b) | Этап 12 |
|---|---|
| `deploy/Dockerfile`, цели `api`, `proxy` | те же образы + `gate-agent`, `backup` |
| `deploy/compose.yml` без профилей | профили `onsite`/`cloud`/`agent`/`tunnel` (ADR-011 §1) |
| Caddy HTTP-01 на публичном домене | DNS-01, split DNS (ADR-011 §2) |
| `oxranactl` update/rollback/backup/restore/bootstrap/status/logs | + `restore-check`, обновление через реестр по тегу |
| доставка образов по SSH из Actions | приватный реестр РФ, `oxranactl update vX.Y.Z` через WireGuard |
| systemd-таймер копий на хосте | контейнер `backup` + restic в S3, автопроверка восстановления |
| `setup-vps.sh` | `INSTALL.md` для сервера в ЛЦ (ОС, ИБП, NTP, сеть) |

## Проверка без сервера

Сессия разработки без Docker-демона проверяет: `shellcheck` всех скриптов; `deploy/test/oxranactl.test.sh` — `oxranactl` на поддельных `docker` и `curl` (идемпотентность, откат при сбое проверки, сбой миграций, откат, копии и их хранение, восстановление, чистый старт, очистка образов); `deploy/test/setup-vps.test.sh` — разбор параметров и запись `.env`; `actionlint` для workflow; `caddy validate` и функциональный прогон Caddyfile с локальным бинарём Caddy (маршруты `/`, `/gate/`, `/api/`, кэш, SPA, 404 для `/assets/`, заголовки) и браузером Chromium (пост под `/gate/` рендерится, вход по ссылке, cookie `Secure`); сборка бандла API и запуск `migrate.js`/`bootstrap.js`/`server.js` из раскладки образа; `pg_dump`/`pg_restore` на локальном кластере. Образы и compose целиком — задача `stand` в CI (`.github/workflows/ci.yml`): сборка, hadolint, разбор compose, `caddy validate` в образе и полный прогон `oxranactl` на runner (первый деплой, повторный, маршруты, чистый старт и отказ второго, копия, обновление, откат, восстановление). Только реальный VPS проверит выдачу сертификата Let's Encrypt, `setup-vps.sh` на чистой Ubuntu и SSH-доставку — это приёмка заказчиком.

## Альтернативы

- **GHCR (или другой реестр) вместо передачи по SSH** — лишний секрет на сервере (токен чтения) или публичные образы; передача по SSH обходится ключом деплоя. Реестр понадобится на этапе 12.
- **Два поддомена (`app.` и `gate.`) или wildcard-запись** — отдельный origin у поста безопаснее, но заказчику две записи DNS и два сертификата; см. «Цена» в п. 1.
- **Watchtower / автообновление из реестра** — обновляет без проверки и без отката; здесь версия переключается только после проверки.
- **Копии контейнером `backup` в compose сразу** — ближе к этапу 12, но таймер хоста проще, виден в `systemctl list-timers` и не зависит от compose; контейнер появится вместе с restic.
- **Ключ деплоя с принудительной командой (`command="…"`)** — безопаснее, но требует диспетчера на сервере, который нельзя проверить без сервера; отложено на этап 12.
- **Docker из пакетов Ubuntu вместо репозитория Docker** — ближе к зеркалам хостера, но старее; оставлен как запасной путь.
- **Kubernetes/k3s** — избыточно для одного сервера (ADR-011).

## Последствия

- API получил `TRUST_PROXY` (доверять `X-Forwarded-For` только за Caddy: от IP зависят ограничение попыток входа и аудит), `APP_VERSION` и точку входа `dist/migrate.js`; `runMigrations` принимает папку миграций (`MIGRATIONS_DIR`).
- Каждый push в любую ветку собирает образы и поднимает стенд на runner: CI стал на несколько минут дольше (задача `stand` идёт параллельно с остальными).
- Первый деплой требует рабочей A-записи: проверка идёт через TLS, без неё он завершится ошибкой, и сообщение об этом называет DNS.
- Стенд — не продакшен: копии на том же сервере, нет мониторинга, ключ деплоя даёт root-эквивалент. Персональные данные: стенд стоит в РФ, но договор-поручение и уведомление РКН (Q-32) ещё не оформлены — вносить ли настоящие ПДн людей на стенд до этого, решает заказчик как оператор; до решения разумно вносить объект, арендаторов и лимиты, а людей и номера — выдуманными. **Решение заказчика (12.10.2026, Q-62):** до закрытия Q-32 на стенде объект, арендаторы и лимиты — настоящие; люди и номера машин — выдуманные.
