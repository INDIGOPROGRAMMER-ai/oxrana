# ADR-007. Модель прав, учёток и устройств

Статус: принято. Учитывает `06_` и `16_` A7, A9, A11.

## Контекст

Три вида субъектов: сотрудники оператора (администратор, согласующий, бухгалтер), пользователи арендаторов (ответственный, заказчик, наблюдатель), посты охраны — **одна учётка на КПП** без личных входов (A11). Права атомарны, проверяются на сервере, «впустить» и «редактировать пропуск» — разные права, администратор не нажимает «Впустить» (A7). Нужна тест-матрица 403 (B12).

## Решение

### Субъекты и аутентификация

| Субъект | Как входит | Что хранится | Срок |
|---|---|---|---|
| Пользователь (`users`) | e-mail/телефон + пароль (argon2id) или код из SMS/e-mail (`login_codes`, этап уведомлений) | cookie `sid` (httpOnly, Secure, SameSite=Lax) → `sessions.token_hash` | 30 дней скользящих; отзыв — удаление строки |
| Устройство поста (`gate_devices`, kind `post`) | один раз: код/QR из админки (`device_enrollments`, 10 мин, одноразовый) → долгоживущий токен | токен в IndexedDB устройства; на сервере только хэш | до отзыва; `last_seen_at` для реестра |
| Агент КПП (`gate_devices`, kind `agent`) | то же, что устройство | то же | то же |
| Страница водителя | `pass_tokens` в URL `/p/{token}` | хэш, срок = конец пропуска + 1 день | отзыв при отмене пропуска |

Токены — случайные 32 байта (base64url), в БД — SHA-256. JWT не используем: отзыв должен действовать немедленно, а проверка по индексу стоит столько же.

Приглашения (`invitations`): ссылка на e-mail или SMS, 7 дней, одноразовая; по переходу пользователь задаёт пароль и сразу активен (D2). Пароль, выданный администратором вручную, — `must_change_password`. Один `user` может иметь назначения в нескольких арендаторах и организациях (A9: приглашения персональные и бесплатные).

**Пользователь — только тот, кто входит в систему** (решение заказчика, 10.10.2026). В PASS24 при создании пропуска нужно выбрать «пользователя», которого ещё и регистрируют отдельно; у нас такого понятия нет:
- пропуск принадлежит **арендатору**; автор (`passes.created_by`) записывается сервером из сессии, поля «пользователь» в форме пропуска нет;
- у человека один арендатор — он его не выбирает нигде; несколько — **переключатель компании в шапке** кабинета (меняет `tenantId` контекста), а не поле в форме;
- водитель и пешеход — данные пропуска (ФИО, телефон), не пользователи; им не нужен вход;
- пользователь заводится приглашением и работает сразу; отдельной «регистрации» и состояния «заведён, но не может войти» не существует — `status = 'invited'` виден администратору как «приглашение не принято» с кнопкой «отправить снова».

### Авторизация

- **Право** — строка-код из `contracts/permissions.ts` (единственный источник; таблица ниже). Роль — набор прав внутри организации; новая роль пуста; шаблоны ролей создаются сидом организации и редактируемы.
- **Назначение роли** имеет область: вся организация · объект · арендатор. Проверка: `can(ctx, permission, {siteId, tenantId})` = есть назначение с этим правом, чья область покрывает запрошенную.
- **Учётка КПП** имеет роль-шаблон «Пост КПП» (права ниже), область = её КПП и объект. Сервер подставляет `gateId` из токена устройства; клиент не может выбрать другой КПП.
- **Проверка на сервере в одном месте:** у каждого маршрута Fastify `config.permission` (или `public: true`); `onRequest`-хук отклоняет без права кодом `403 {code:'forbidden', permission, settingLink}`. Маршрут без `config.permission` не стартует (проверка при регистрации). Тест-матрица: для каждого маршрута × каждой роли шаблона ожидание 2xx/403 — таблица в `apps/api/test/permissions.matrix.ts`.
- Пользователь арендатора: все запросы дополнительно ограничены `tenantId` из его назначений; попытка указать чужой `tenantId` → 403 (не 404).
- Видимость ≠ разрешение: пост видит все пропуска объекта, а КПП влияет только на вердикт (A4/A5 из `03_`).

### Шаблоны ролей (сид организации)

| Роль | Область | Права |
|---|---|---|
| Владелец организации | организация | все, включая `role.manage`, `user.manage` |
| Администратор объекта | объект | все, **кроме** `visit.check_in/out`, `gate.redirect/refuse/undo/passage` (A7) и биллинга |
| Согласующий | объект | `pass.view_all_tenants`, `pass.approve`, `pass.change_request.decide`, `pass.history.view`, `report.view`, `occupancy.view` |

| Старший смены (необязательно, через PIN) | КПП | Пост КПП + `gate.override` |

| Арендатор — наблюдатель | арендатор | `pass.view`, `pass.history.view`, `occupancy.view` |

### Запрос исключения (A11)

Пост при 🟡/🔴 нажимает «Запросить исключение» → `override_requests(pending)` + событие → push/Telegram/e-mail пользователям с `gate.override` на объекте. Одобрение одним нажатием (`POST /override-requests/{id}:approve`, причина видна) → `valid_until = now + overrideValidMin` → событие на пост → карточка зелёная; «Впустить» выполняет `checkIn` с `overrideId`, визит получает `override_id`, журнал — КПП, устройство, кто одобрил, причина (сценарий 42). «PIN старшего смены» (настройка объекта, по умолчанию выключена) одобряет тот же запрос локально с `via = 'senior_pin'`.

### Необязательная отметка смены

При `shiftMarkEnabled` пост в начале смены предлагает выбрать имя из списка (`shift_marks`, без PIN); имя пишется в `snapshot` решений как `guardName`. На права не влияет.

## Альтернативы

- **Личные учётки охранников с PIN** (как в `01_`/`07_`): отменено заказчиком (A11).
- **JWT без состояния**: не отзываются мгновенно; у нас отзыв устройства — обязательный сценарий.
- **Права на «модули-экраны»**: ошибка PASS24 (E4); у нас права на действия, экран сам скрывает/дизейблит с причиной.
- **Наследование прав роли-родителя**: ошибка PASS24 (E3).
- **Один пользователь = одна организация**: мешает арендаторам с несколькими площадками и подрядчикам.

### Новое право (этап 6b.1)

Проверка 6b на стенде показала дыру: владелец создан до миграции 0007, в его роли нет прав 6b, а выдать их себе нельзя («не шире своих прав», ADR-018 п. 5). Тесты этого не ловили: организация в них создаётся после всех миграций. Решение:

- **Новое право → миграция, выдающая его ролям по шаблонам.** Права добавляются в `PERMISSIONS` и в `ROLE_TEMPLATES`, затем в `packages/db/migrations` появляется миграция `NNNN_role_templates_sync.sql`, полученная `pnpm --filter @oxrana/db role-sync-sql`: каждой роли с `template_code` добавляются права её шаблона, которых в роли нет (лишние права роли не трогаются). Миграция несёт полный снимок шаблонов, поэтому последняя из них заменяет предыдущие. Тест `packages/db/test/role-sync.integration.test.ts` сверяет последнюю такую миграцию с `ROLE_TEMPLATES` (шаблон поменяли, миграцию забыли — красный) и выполняет её на ролях «старого состояния».
- Побочное следствие: право, которое администратор намеренно снял у роли-шаблона, миграция вернёт, если оно есть в шаблоне. Это цена простого правила «роль по шаблону не отстаёт от шаблона»; осознанно сузить роль после миграции можно снова.
- **Владелец организации (`org_owner`) всегда имеет все права `PERMISSIONS`** независимо от массива в БД: при сборке актора (`userGrants`) для роли с `template_code = 'org_owner'` права берутся из реестра, а не из БД. Выбрано вместо синхронизации при каждом `migrate`: там, где владелец не может забыть право, миграция становится страховкой, а не единственной защитой, и правка не зависит от того, запущен ли `db:migrate`. Для остальных ролей по шаблонам права из БД — как есть (их можно сужать).

### История пропуска и учётка КПП (этап 7b.3)

Право `pass.history.view` («История пропуска: изменения и отметки КПП») даёт **ленту пропуска** (`GET /passes/:id/history`) и заявки на изменение пропуска (`GET /passes/:id/change-requests`). Карточка пропуска с данными (`GET /passes/:id/card`) открывается по `pass.view | pass.view_all_tenants` — без истории: вместо ленты неактивная строка с причиной.

- **Шаблоны:** владелец (все права), «Администратор объекта», «Согласующий», три роли арендатора (история в кабинете у них уже была — не отнимаем). «Пост КПП» и «Старший смены» **без права**: у них есть `pass.view_all_tenants`, но охране лента — это чужой журнал и обход «светофора».
- **Учётка КПП не получает право никогда.** `NEVER_FOR_GATE_ACCOUNT_PERMISSIONS` (contracts): актор поста собирается без этих прав (`actorFromGrants` для `kind = 'gate_account'`), поэтому даже если право добавили в роль учётки (SQL, ручная правка), сервер отвечает 403. Редактор ролей у ролей области «КПП» (шаблоны с `scope = 'gate'` и любая роль, назначенная учётке КПП; в `GET /roles` — `forGate`) показывает переключатель неактивным с причиной, `PATCH /roles/:id` отклоняет выдачу (`validation_failed`, поле `permissions`). В `apps/gate` вызовов ленты и карточки нет (тест `apps/gate/test/no-history.test.ts`).
- **Миграция `0015_pass_history_role_templates_sync.sql`** выдаёт право существующим ролям по шаблонам (правило «новое право → миграция»); владелец получает его при сборке актора независимо от массива в БД.
- Не путать: `pass.view` — видеть пропуска; `pass.history.view` — видеть, кто что менял и когда охрана впускала.

## Реализация хука (этап 1)

`apps/api/src/permission-guard.ts`, подключается на корневом экземпляре Fastify до маршрутов:
- `onRoute`: маршрут без `config.permission` и без `public: true` — исключение при регистрации, сервер не стартует; то же для `public: true` вместе с `permission` и для права, которого нет в реестре (`PERMISSIONS` из `contracts`, пока список пуст — тесты передают свой реестр). Тип `config.permission` — `string`: допустимость кода проверяется при регистрации, а не типом, пока реестр пуст.
- `onRequest`: публичные маршруты пропускаются; иначе нужен актор (`resolveActor`, до этапа 5 по умолчанию никого не находит). Нет актора → `401 unauthenticated`; нет права → `403 forbidden` с полями `permission` и `settingLink: '/admin/roles'`. Проверка идёт до разбора тела запроса.
- **401 или 403 (решение заказчика 10.10.2026, Q-47):** `401 unauthenticated` — запрос без входа: нет cookie-сессии или токена устройства, либо они истекли или отозваны; клиент ведёт на вход (пост — на экран привязки). `403 forbidden` — вход есть, но у актора нет права на это действие в этой области (в том числе чужой `tenantId`); клиент показывает причину и `settingLink`, на вход не уводит. Тест-матрица этапов 4–5 проверяет обе ветки для каждого маршрута.
- Формат ошибки — `ErrorBody` из `contracts/errors.ts`: `{code, message, field, settingLink, requestId}` (+ `permission` для `forbidden`). Технические коды каркаса: `bad_request`, `validation_failed`, `unauthenticated`, `forbidden`, `not_found`, `unavailable`, `internal`; `unauthenticated` и `unavailable` — новые относительно текста выше. `settingLink` — путь экрана веб-интерфейса, где причину можно исправить, или `null`.

## Последствия

- Добавление маршрута без `config.permission` ломает запуск — нельзя забыть проверку.
- Тест-матрица растёт с каждым маршрутом; это цена гарантии B12.
