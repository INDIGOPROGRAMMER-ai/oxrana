# ADR-004. Realtime: outbox → LISTEN/NOTIFY → SSE

Статус: принято.

## Контекст

Пост и кабинет обновляются без F5 (сценарии 3, 15, 40, 42): карточка меняет цвет при выезде чужой машины, запрос «без пропуска» приходит на телефон ответственного за секунды, одобрение исключения — на пост. Realtime нужен и уведомлениям (почта, push, Telegram), и агенту КПП (команды). Без Redis (B8).

## Решение

1. **Transactional outbox.** Любое изменение, о котором должен узнать кто-то ещё, пишет строку в `domain_events` **в той же транзакции**, что и само изменение. Нет отдельной «публикации» — нечему потеряться.
2. **Триггер `AFTER INSERT` на `domain_events`** делает `pg_notify('site_events', '{"siteId":…,"id":…}')`. Полезная нагрузка NOTIFY — только идентификаторы (лимит 8 КБ и отсутствие гарантий доставки нас не касаются: данные читаются из таблицы).
3. **API держит одно выделенное соединение `LISTEN site_events`** (не из пула) с переподключением; при получении читает событие по `id` и рассылает подписчикам в памяти процесса. Несколько инстансов API — каждый слушает сам, координация не нужна.
4. **SSE-эндпоинт** `GET /sites/{siteId}/events` (для поста — `GET /gate/events`, для агента — `GET /agent/events`): `text/event-stream`, `id:` = `domain_events.id`, `retry: 3000`, heartbeat-комментарий каждые 25 с. Фильтр по правам: пользователь арендатора получает только события своего арендатора (`payload.tenantId`) и общие (`quota.changed` по своим квотам); пост — события своего объекта; агент — только `command.*` своего КПП.
5. **Воспроизведение.** При переподключении браузер шлёт `Last-Event-ID`; сервер отдаёт из таблицы всё с большим `id` (не старше `retentionDays`, иначе — `event: resync` → клиент перечитывает состояние). Это же закрывает возвращение поста из офлайна (ADR-005).
6. **Клиент:** `EventSource` + TanStack Query: событие инвалидирует нужные ключи (`['occupancy', siteId]`, `['pass', id]`), а не несёт полное состояние. Для поста — ещё звук и локальное обновление снимка.
7. **Уведомления и вебхуки** — потребители того же outbox: pg-boss задача `dispatch-events` с курсором по `domain_events.id` создаёт `notifications` и отправляет. Одна запись — много потребителей, у каждого свой курсор.

Типы событий (в `contracts/events.ts`): `pass.created|updated|status_changed`, `visit.opened|closed|undone`, `quota.changed` (`{quotaId, occupied, capacity}`), `gate_request.created|answered`, `override.requested|decided`, `queue.slot_freed` (`{passId, gateId}`), `rules.changed`, `lpr.candidate`, `barrier.result`, `command.issued` (агенту).

## Альтернативы

- **WebSocket** (`@fastify/websocket`): двусторонность не нужна — команды вверх идут обычными POST с идемпотентными ключами; SSE проходит через любые прокси, переподключается сам, `Last-Event-ID` встроен. Для агента КПП то же: исходящее соединение SSE + POST.
- **Короткий polling** каждые 2–3 с: простая, но на 3 постах и 30 вкладках кабинетов это постоянная нагрузка и задержка; не даёт звука «место освободилось» вовремя.
- **Redis pub/sub / NATS**: лишний сервис (B8). `LISTEN/NOTIFY` покрывает масштаб одного-десяти объектов с запасом.
- **NOTIFY с полной нагрузкой без таблицы**: теряется при отсутствии слушателя, нет воспроизведения.

## Последствия

- Каждая доменная операция — это транзакция «изменение + событие + аудит». Сервисный слой даёт `tx.emit(event)`, вне транзакции `emit` недоступен.
- Таблица `domain_events` растёт: партиционирование по месяцу с этапа отчётов, чистка по сроку.
- SSE через nginx требует `proxy_buffering off` и `X-Accel-Buffering: no` — зафиксировано в конфиге деплоя.
