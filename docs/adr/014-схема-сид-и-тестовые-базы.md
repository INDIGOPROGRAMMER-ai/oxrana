# ADR-014. Схема БД, миграции, сид и тестовые базы (этап 2)

Статус: принято (10.10.2026, этап 2). Дополняет ADR-003, 004, 010, 012; уточняет детали, которых в них нет, и фиксирует, где реализация от них отошла.

## Контекст

Этап 2 превращает `DATA_MODEL.md` в работающую БД: 54 таблицы, RLS по организации, exclusion-ограничения, триггеры, outbox, демо-сид и тестовые базы на реальном PostgreSQL. По ходу пришлось выбрать: где описывать RLS и `check` (в схеме Drizzle или руками в SQL), как сделать сид идемпотентным, как изолировать интеграционные тесты, как считать «где используется» для мягкого удаления.

## Решение

1. **Всё, что Drizzle умеет, — в схеме `packages/db/src/schema`, а не в SQL руками:** таблицы, `check`, частичные и выражающие индексы, внешние ключи, `UNIQUE NULLS NOT DISTINCT`, политики RLS (`pgPolicy`). Тогда снимок drizzle-kit знает о них, и следующая генерация не потеряет и не продублирует их. Имена колонок — явно в snake_case (без настройки `casing`): SQL миграций и запросы читаются одинаково.
2. **Миграции.** `0001_schema.sql` — целиком сгенерирован `drizzle-kit generate` и руками не правится. То, чего Drizzle не выражает, — отдельной ручной миграцией (`drizzle-kit generate --custom`): `0002_constraints_triggers_grants.sql` — exclusion-ограничения, функция и триггеры `set_updated_at`, outbox-триггер, урезание прав на журналы. Так ревью видит «сгенерированное» и «написанное руками» раздельно (ADR-003 п. 2 предлагал дописывать в тот же файл — отказались ради этой прозрачности). Имена внешних ключей длиннее 63 символов задаются явно (`foreignKey({ name })`), иначе Postgres молча обрезает их.
3. **Перечисления.** Списки значений — в `packages/contracts/src/enums.ts` (массив + `z.enum` + тип). Схема строит из того же массива и тип колонки (`text(…, { enum })`), и `check` с именем `<таблица>_<колонка>_check` (`enumCheck`, для массивов — `<@`, `enumArrayCheck`). Интеграционный тест читает `check` из применённых миграций и сравнивает с `options` zod-схем; «лишний» `check` без описания в contracts — тоже ошибка.
4. **RLS.** Политика `organization_isolation` — на 48 таблицах: 45 с `organization_id`, `organizations` (`id = …`) и две связки (ниже): `organization_id = nullif(current_setting('app.organization_id', true), '')::uuid` в `USING` и `WITH CHECK`. `nullif` нужен, потому что после `set local` в прошлой транзакции настройка в том же соединении становится пустой строкой, а не `null`. Таблицы-связки без `organization_id` (`quota_categories`, `time_window_policy_categories`) защищены через родителя: `exists (select 1 from quotas p where p.id = quota_id)` — подзапрос сам проходит RLS родителя. Платформенные таблицы (`users`, `sessions`, `login_codes`, `push_subscriptions`, `notification_preferences`, `telegram_links`) без RLS: пользователь состоит в нескольких организациях, доступ к ним — в сервисном слое (этап 5). Контекст ставит `withOrganization(db, orgId, fn)` из `@oxrana/db` (`set_config(…, true)` = `set local`). Владелец таблиц (`oxrana_owner`: миграции, сид) RLS не подчиняется — `FORCE ROW LEVEL SECURITY` не включаем.
5. **Outbox.** Триггер `AFTER INSERT` на `domain_events` → `pg_notify('site_events', {"id","organizationId","siteId"})`. К идентификаторам из ADR-004 добавлен `organizationId`: слушатель читает событие под RLS и должен знать, какую организацию выставить. Уведомление уходит только при `COMMIT`.
6. **Права на журналы.** `oxrana_app` без `UPDATE`/`DELETE` на `audit_log`, `domain_events`, `gate_decisions`, `hardware_events` (ADR-003 п. 4) и без `DELETE` на `visits` и `barrier_commands` (их обновляют выезд и статус команды, но не удаляют).
7. **Тестовые базы.** Глобальный setup Vitest пересоздаёт `oxrana_test_template` **при каждом прогоне** и применяет миграции (≈1 с) — правка миграции в работе не оставит устаревшую схему. `setupFiles` (`packages/db/test/worker-setup.ts`) перед **каждым тестовым файлом** делает свежую копию `oxrana_test_w<VITEST_POOL_ID>` из шаблона (≈0,2 с) и переводит на неё `DATABASE_URL`/`DATABASE_ADMIN_URL`. Файлы не видят данных друг друга; внутри файла тесты используют уникальные данные. Базы воркеров удаляются после прогона, шаблон остаётся для разбора. Шаблон создаёт сам setup (роли `oxrana_owner` хватает `CREATEDB`), поэтому `db-up.sh` его не создаёт — в отличие от ADR-010 п. 1. Сид в шаблон не входит: тесты, которым нужен демо-объект, применяют его сами (≈0,3 с).
8. **Сид** (`packages/db/seed`, `pnpm db:seed`). Данные — декларативное описание `SeedData` (`radonezhsky.ts`), применение — `applySeed(db, data)` в одной транзакции под владельцем. **Идемпотентность:** id каждой строки — UUIDv5 от естественного ключа (`integratsiya/tenant/dns`), вставка — `on conflict do nothing` без цели конфликта. Повторный запуск ничего не дублирует, **не меняет** строки, которые уже есть (в том числе отредактированные администратором), и дописывает недостающие. Организация с тем же `slug`, созданная не сидом, — ошибка с объяснением, а не тихое смешение данных. До записи сид проверяет свои данные: ссылки по ключам, док не у двух арендаторов, `capacity` лимита «по докам» = числу доков в лимите, zod-схемы `jsonb`. Сомнительное — список `checkList` (печатается после запуска) и пометки «ПРОВЕРИТЬ» в `contracts.notes`, `contract_clauses.summary`, `exceptions.basis`. Названия объекта живут только в `packages/db/seed` (ADR-012 п. 7).
9. **Мягкое удаление с подсчётом ссылок** (сценарий 32, CLAUDE.md п. 10): `findUsages(db, table, id)` перебирает внешние ключи всех таблиц схемы, указывающие на таблицу, и считает ссылки, не учитывая мягко удалённые строки; `softDelete(db, table, id)` ставит `deleted_at`. Новая таблица со ссылкой попадает в подсчёт без правки кода.
10. **Права и шаблоны ролей заполнены на этапе 2**, а не 4–5: `PERMISSIONS` (коды ADR-007) и `ROLE_TEMPLATES` в `contracts` нужны сиду для ролей и учёток КПП. Маршрутов с этими правами пока нет.

## Альтернативы

- **RLS и `check` руками в SQL** (как предполагал ADR-003): снимок drizzle-kit о них не знает; ошибка в именах или забытая таблица видны только в рантайме. Схема с `pgPolicy` даёт ту же SQL и проверку типов.
- **Postgres `enum`**: запрещён соглашением DATA_MODEL (блокирующие `ALTER TYPE`).
- **Сид через `on conflict … do update`** (приводить к эталону при каждом запуске): затирал бы правки администратора на демо-стенде — это «ломает данные». Для эталонного состояния есть `pnpm db:reset`.
- **Уникальные индексы на естественные ключи** (`tenants (site_id, short_name)` и т. п.) ради идемпотентности сида: меняют модель ради демо-данных; детерминированные id не требуют изменений схемы.
- **Одна база на воркер с откатом транзакции после каждого теста**: не работает для тестов с несколькими соединениями (гонки ADR-006, LISTEN/NOTIFY) — им нужен коммит. Копия шаблона на файл дешевле, чем `TRUNCATE` всех 54 таблиц, и не зависит от порядка.
- **Колонка `organization_id` в таблицах-связках**: денормализация ради RLS, которую политика через родителя даёт и так.

## Последствия

- Изменение схемы: `DATA_MODEL.md` → `src/schema/*.ts` → `pnpm --filter @oxrana/db generate` → при необходимости ручная миграция `--custom`. Тест «схема в БД = схема Drizzle» ловит забытую миграцию, тест перечислений — рассинхрон contracts и `check`, структурный тест — таблицу с `organization_id` без RLS и таблицу с `updated_at` без триггера.
- API (этап 4) обязано открывать транзакцию через `withOrganization` и всё равно фильтровать по `organization_id` явно.
- Каждый интеграционный тестовый файл стоит ≈0,2 с на копию базы; при сотнях файлов вернёмся к пулу заранее созданных копий.
