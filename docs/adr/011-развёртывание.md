# ADR-011. Развёртывание: на объекте и в облаке

Статус: принято (10.10.2026). Заменяет раздел «Деплой» ADR-010 (п. 7) и первую редакцию `ARCHITECTURE.md` §7.

## Контекст

Решение заказчика: **основной режим — сервер на территории ЛЦ**, облако — второй режим того же дистрибутива для будущих клиентов SaaS. При этом арендаторы заказывают пропуска из офисов и с телефонов, администратор работает удалённо, в том числе из другой страны. Посты и оборудование КПП должны работать при отсутствии интернета на объекте; офлайн-режим PWA (ADR-005) остаётся на случай отказа самого сервера. Данные — на сервере оператора (152-ФЗ). Наружу выставляются только веб и API.

## Решение

### 1. Один дистрибутив, два режима

Дистрибутив — Docker Compose (`deploy/compose.yml`) с одним набором образов. Режим задаётся переменной `DEPLOY_MODE=onsite | cloud` и профилями compose; код приложения о режиме не знает.

| | `onsite` (основной) | `cloud` |
|---|---|---|
| Где | сервер в серверной ЛЦ, LAN объекта | VPS/VM в ЦОД РФ |
| Сервисы | `caddy`, `api`, `postgres`, `gate-agent` (профиль `agent`), `backup`, `wg-client` (профиль `tunnel`), `nut` (ИБП) | `caddy`, `api`, `postgres`, `backup` |
| Доступ постов | по LAN, напрямую к серверу | через интернет |
| Доступ извне | вариант А (белый IP) или Б (туннель на VPS-шлюз), см. §3 | напрямую, Caddy на VM |
| Бэкап вне площадки | S3 РФ или VPS-шлюз | S3 РФ в другом ЦОД |
| Интернет пропал | КПП, табло, кабинет из LAN работают; снаружи недоступно; уведомления встанут в очередь | — |
| Сервер отказал | посты — офлайн-режим PWA | посты — офлайн-режим PWA |

### 2. Сеть объекта: посты по LAN с тем же доменом

- У сервера статический адрес в LAN (например `10.20.0.10`), посты, камеры и реле — в той же сети или в маршрутизируемом сегменте «КПП».
- **Один домен снаружи и внутри**, например `pass.example.ru` (вопрос Q-31d). Внутри сети он разрешается в LAN-адрес сервера (**split DNS**): локальный DNS — на самом сервере (`dnsmasq` в compose, профиль `onsite`) либо запись на маршрутизаторе объекта; DHCP выдаёт постам этот DNS. Резерв — строка в `hosts` на ПК поста (вписывается установщиком, инструкция в комплекте).
- **TLS — публичный сертификат Let's Encrypt через DNS-01** (Caddy, провайдер DNS из списка поддерживаемых — вопрос Q-31d): получается и продлевается только исходящими запросами, поэтому работает и без белого IP и без открытого 80-го порта. Тот же сертификат обслуживает LAN и интернет.
- **PWA**: origin один и тот же в LAN и в интернете → одна установка, один service worker, одна база IndexedDB. Устройство поста, перенесённое в другую сеть (LTE, другой офис), резолвит публичный адрес и продолжает работать через интернет; вернулось в LAN — снова напрямую. Ничего переустанавливать и перепривязывать не нужно. Устройство, переехавшее на другой КПП, — отзыв и новая привязка (ADR-007): учётка = КПП.
- Агент КПП и камеры — только LAN; вовне они не видны.

### 3. Доступ извне

**Вариант А — белый IP.** На маршрутизаторе объекта проброс только `443/tcp` (и `80/tcp` для редиректа) на Caddy сервера; `51820/udp` — WireGuard-сервер на сервере для администратора. Ничего больше. Минус: зависимость от провайдера и статического адреса; при смене провайдера — перенастройка; нет внешней точки для мониторинга.

**Вариант Б — туннель на VPS-шлюз (рекомендуемый, стандарт дистрибутива).** Небольшой VPS в РФ (1 vCPU, 1 ГБ, ~300–500 ₽/мес) с публичным IP. Сервер объекта поднимает **исходящий** WireGuard-туннель к VPS (`wg-client`, keepalive 25 с). На VPS — `nginx stream` с `ssl_preread`: принимает `443/tcp` и **пропускает TLS без расшифровки** по SNI в туннель на Caddy сервера объекта. Ключи TLS и данные VPS не видит. VPS также: точка входа администратора (WireGuard-пир, SSH на сервер только через туннель), внешний монитор (§7), резервная цель бэкапов (§5). Белый IP у объекта при этом не нужен; смена провайдера на объекте ничего не меняет.

Рекомендация — **Б как основной**: предсказуемо, не зависит от провайдера, даёт удалённое обслуживание и мониторинг «из коробки». А — когда у объекта уже есть белый IP и заказчик не хочет VPS; оба описаны в инструкции установки, выбор — флагом `INGRESS=direct | tunnel`.

Наружу в обоих вариантах только Caddy (веб и API). PostgreSQL слушает только docker-сеть; SSH, панели, `/docs` OpenAPI, метрики — только через WireGuard.

### 4. Внешние сервисы — только исходящие соединения

| Сервис | Как |
|---|---|
| Telegram | бот через **long polling** (`@grammyjs/runner`), вебхук не используется |
| E-mail | SMTP с TLS к провайдеру РФ |
| SMS | HTTPS к провайдеру |
| Web Push | HTTPS к push-сервисам браузеров (payload зашифрован, без ПДн); требует интернет у получателя, не у поста |
| Let's Encrypt | DNS-01, исходящие запросы к API DNS-провайдера |
| Образы | `docker pull` из приватного реестра |
| Бэкапы, мониторинг | исходящие к S3/VPS |

Очередь уведомлений (pg-boss) переживает отсутствие интернета: отправка повторяется с экспоненциальной задержкой до 24 ч, затем помечается `failed`.

### 5. Бэкапы

- **Локально:** `pg_dump -Fc` ежедневно в 02:00 местного времени + непрерывный архив WAL (`archive_command` на локальный диск) → восстановление на любой момент за последние 7 дней.
- **Вне объекта, обязательно, зашифровано:** `restic` (AES-256, ключ у оператора, хранится в сейфе/парольном менеджере, не на сервере в открытом виде — передаётся контейнеру через секрет) отправляет дампы, WAL и каталог файлов (договоры, фото) в **S3 РФ** (основная цель) или на **VPS-шлюз по SFTP** (если S3 недоступен). Хранение: 30 ежедневных, 12 ежемесячных.
- **Проверка восстановления — автоматическая, еженедельно:** контейнер `backup` разворачивает последний дамп в `oxrana_restore_check`, сверяет число строк в `passes`, `visits`, `audit_log` с эталоном, выполняет `pnpm db:migrate --check`, пишет результат в журнал и уведомление администратору платформы. Непройденная проверка — инцидент.
- Ручное восстановление описано в `deploy/RESTORE.md` и прогоняется при приёмке этапа 12.

### 6. Обновления и обслуживание — удалённо

- Образы (`api`, `caddy` со статикой `web`/`gate`, `gate-agent`, `backup`) собираются в CI по тегу `vX.Y.Z` и публикуются в **приватный реестр в РФ** (Yandex Container Registry; вопрос Q-31f). На сервере — pull-токен только на чтение.
- Обновление: `oxranactl update vX.Y.Z` (скрипт в дистрибутиве): `pull` → бэкап → миграции (обратно совместимые на один релиз, ADR-003) → `up -d` → проверка `/healthz` и smoke-запроса → при ошибке `oxranactl rollback` на предыдущий тег (образы предыдущей версии не удаляются). Окно — ночью, посты в это время работают офлайн-режимом до 1–2 мин.
- Доступ администратора платформы — только через WireGuard (пир на VPS или на сервере), затем SSH по ключам; паролей нет; sudo с журналом. Доступ администратора объекта — через веб.
- Все команды обслуживания — через `oxranactl` (update, rollback, backup, restore-check, status, logs), чтобы обслуживание не зависело от знания compose.

### 7. Мониторинг извне

- На VPS-шлюзе — **Uptime Kuma** (self-hosted): проверяет `https://pass.example.ru/healthz` через туннель каждую минуту, возраст последнего WireGuard-handshake, срок сертификата, свободное место (по `/healthz` с токеном). Алерты — Telegram и e-mail администратору платформы.
- Сервер объекта дополнительно шлёт **heartbeat** на VPS раз в минуту (dead-man switch): пропал сервер, туннель или питание — уведомление в течение 3 минут.
- Ошибки приложения — GlitchTip/Sentry self-hosted на VPS (вопрос Q-36), без ПДн в событиях.
- В режиме `cloud` тот же Uptime Kuma живёт на отдельной маленькой VM.

### 8. Железо сервера объекта

| | Минимум | Рекомендуется |
|---|---|---|
| CPU | 4 ядра x86-64 | 8 ядер |
| RAM | 16 ГБ ECC желательно | 32 ГБ ECC |
| Диски | 2 × 512 ГБ NVMe/SSD в зеркале (mdadm RAID1 или ZFS mirror) | 2 × 1 ТБ NVMe в зеркале + отдельный SSD под локальные бэкапы |
| Сеть | 1 GbE | 2 × 1 GbE (LAN объекта + сегмент КПП/камер) |
| ИБП | онлайн/линейно-интерактивный ≥ 15 мин, USB-сигнал → `nut`: корректное выключение при 20 % заряда | ≥ 30 мин, питание также на коммутатор КПП и маршрутизатор |
| ОС | Ubuntu Server 24.04 LTS, автообновления безопасности, Docker CE | то же |
| Время | `chrony` → NTP пул + маршрутизатор объекта; RTC с батарейкой; расхождение > 2 с — алерт (вердикты зависят от времени, ADR-009) | то же + локальный NTP для постов и камер |
| Форм-фактор | мини-ПК/тауэр в закрываемом шкафу серверной, доступ только у оператора | 1U в стойке |

Нагрузка на Радонежском (3 поста, 12 арендаторов, сотни событий в день) далека от пределов минимума; требования продиктованы надёжностью и сроком хранения.

### 9. 152-ФЗ в режиме «на объекте»

- Персональные данные хранятся и обрабатываются на сервере, принадлежащем оператору ПДн (ООО «Интеграция»), на его территории; трансграничной передачи нет; администратор из другой страны работает через веб-интерфейс по TLS и видит данные, но не копирует базу (экспорт — только по праву `report.export`, с записью в аудит).
- VPS-шлюз пропускает TLS без расшифровки и хранит только зашифрованные бэкапы (ключ у оператора) — он не обрабатывает ПДн в открытом виде. Провайдер VPS и S3 — РФ.
- Разработчик платформы получает доступ к серверу только через WireGuard по поручению оператора (договор-поручение, Q-32), действия журналируются.
- В режиме `cloud` платформа — обработчик по поручению оператора; ЦОД — РФ.

## Альтернативы

- **Только облако (VPS)** — первая редакция. Отвергнуто заказчиком: КПП должны работать без интернета, данные — на объекте.
- **Cloudflare Tunnel / ngrok / аналоги** вместо WireGuard + VPS: иностранные сервисы, трафик и TLS-терминация за рубежом — не проходит по 152-ФЗ.
- **TLS-терминация на VPS** (обычный reverse proxy): проще, но ключи и расшифрованный трафик на чужой машине; `ssl_preread`-passthrough снимает это ценой одной настройки.
- **Внутренний домен с собственным CA** для постов: два origin → две PWA и распространение корневого сертификата на каждое устройство; split DNS с публичным сертификатом проще и переживает перенос устройства.
- **Самодельный туннель по SSH / autossh**: менее надёжен, нет keepalive-семантики и роуминга WireGuard.
- **Kubernetes/k3s**: избыточно для одного сервера; compose + `oxranactl` понятнее обслуживающему персоналу.
- **Бэкап только локально / только дампы без WAL**: не отвечает требованию копии вне объекта и восстановления на момент времени.

## Последствия

- В комплекте дистрибутива (этап 12): `compose.yml` с профилями, `oxranactl`, `INSTALL.md` (сеть, DNS, DNS-01, ИБП, NTP), `RESTORE.md`, конфиг VPS-шлюза (`nginx stream`, WireGuard, Uptime Kuma), чек-лист приёмки.
- Приложение не зависит от режима: один образ, одни миграции, `DEPLOY_MODE` влияет только на compose.
- Офлайн-режим PWA остаётся обязательным (ADR-005): он покрывает отказ сервера и плановые обновления.
