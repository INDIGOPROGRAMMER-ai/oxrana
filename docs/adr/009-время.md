# ADR-009. Время и часовые пояса

Статус: принято.

## Контекст

Главная системная ошибка PASS24 (E1, §16.5 справки): один пропуск в трёх поясах на трёх экранах; администратор западнее Москвы не может создать пропуск «на сейчас». Объект — UTC+5, администраторы бывают в других поясах; сценарии 6, 7, 9, 22 требуют детерминированного времени в тестах.

## Решение

1. **Хранение:** только `timestamptz`; `date` — для «местных суток» (начисления, отчёты), вычисленных в поясе объекта в момент записи и подписанных им. Сервер и БД работают в `TZ=UTC` (проверка при старте: `show timezone` = UTC, иначе процесс не стартует).
2. **Пояс — свойство объекта** (`sites.timezone`, IANA). Пояс браузера и сервера не читаются нигде: линт-правило запрещает `new Date().getTimezoneOffset`, `toLocaleString` без `timeZone`, `Date.now()` вне `clock`.
3. **На границе API** время — ISO-8601 с `Z`. Формы отправляют мгновение, собранное из локальных полей **в поясе объекта** (`@date-fns/tz`: `TZDate`), а не в поясе браузера. Каждый экран подписывает пояс: «14:32 (Челябинск, UTC+5)».
4. **Движок** получает `now: number` (мс UTC) и `site.timezone`; локальные вычисления (сутки сверхлимита, рабочее время, тексты «въезд с 14:00») — через `Intl.DateTimeFormat(…, {timeZone})`. Никаких библиотек дат в `engine`.
5. **Инжектируемые часы:** интерфейс `Clock { now(): number }` передаётся в сервисы API; в тестах — `FixedClock`/`SteppingClock`. pg-boss-задачи получают `now` из `clock` тоже. Vitest — `vi.useFakeTimers` не используем (ломает pg); только `Clock`.
6. **Валидация «не в прошлом»** — только при создании и только при изменении поля начала (B2); сравнение с `clock.now()`, а не с временем браузера.
7. **Рабочее время и расписания** (`working_hours`, `quota.schedule`) — локальные часы объекта и дни недели; переход через полночь (`["22:00","06:00"]`) допускается и тестируется.
8. **Тесты на пояс:** набор сценариев прогоняется для `Asia/Yekaterinburg`, `Europe/Kaliningrad`, `Asia/Kamchatka`; сценарий 22 — клиент с `TZ=America/Chicago` в Playwright создаёт пропуск «на сейчас» без ошибки.

## Альтернативы

- Хранить локальное время объекта (`timestamp`): ломается при смене пояса объекта и при объектах в разных поясах у одной организации.
- Luxon/Temporal в движке: зависимость и размер в бандле поста; `Intl` достаточно для форматирования и разбиения на сутки.
- Определять пояс по браузеру «для удобства»: ровно ошибка PASS24.

## Последствия

- В UI нет ни одного `new Date().toLocale…` без явного `timeZone` объекта. Общий хелпер `fmt(instant, site)` в `packages/ui`.
- Отчёты за «день» всегда означают местные сутки объекта, и это написано в шапке отчёта.

## Дополнение: пояс по умолчанию, смена пояса, «моё время» (решение заказчика 10.10.2026)

Пояс по-прежнему — свойство объекта (п. 2). Добавлено:

1. **Пояс по умолчанию у организации** — `organizations.default_timezone` (IANA, может быть не задан). Форма нового объекта предзаполняется им; рядом — подсказка по адресу: «по адресу „г. Новосибирск“ объект в поясе Новосибирск, UTC+7 — проверьте», если пояс по словарю городов (`packages/contracts`, `suggestTimezone`) отличается от предзаполненного. API: `GET /org/site-defaults?address=` возвращает пояс по умолчанию и подсказку; `POST /sites` без `timezone` берёт пояс организации и возвращает его в ответе, а если пояс организации не задан — ошибка `timezone_required` с полем `timezone`. Подсказка — только подсказка: пояс по адресу сам не подставляется.
2. **Смена пояса объекта** — отдельное действие `POST /sites/{id}/timezone` с правом `site.manage`, обязательной причиной и подтверждением. Без `confirm: true` сервер отвечает `409 confirmation_required` и текстом последствий: прошлые записи хранятся в UTC и не меняются, но на экранах будут показаны в новом поясе; «местные сутки» прошлого (начисления, отчёты за дни до смены) не пересчитываются; рабочее время, расписания лимитов и окна в правилах — местные часы и начнут действовать в новом поясе. Смена пишется в аудит (было → стало, причина) и рассылает `site.timezone_changed` и `rules.changed`. Обычный `PATCH /sites/{id}` пояс не меняет и называет нужное действие.
3. **Личная настройка «показывать ещё и моё время»** — `users.show_own_time` (по умолчанию выключена) и `users.own_timezone` (пользователь выбирает свой пояс из списка; пояс браузера не читается, п. 2). Основное время на всех экранах — **всегда время объекта с подписью пояса**; своё — только мелкой второй строкой: «14:32 (Челябинск, UTC+5)» · «у вас 04:32, Чикаго». Заменять время объекта временем пользователя нельзя ни в какой настройке. API: `GET/PATCH /me/settings`.
4. **Сводные экраны по нескольким объектам** — у каждого объекта своё время со своей подписью; общего «серверного» или «браузерного» времени нет. Ответы API, где встречаются несколько объектов (`GET /sites`, `GET /occupancy`), несут у каждого объекта `timezone` и готовую подпись `timezoneLabel`.
5. Подпись пояса — `timezoneLabel(tz, at, city?)` из `packages/contracts`: «Челябинск, UTC+5». Город — из адреса объекта, если словарь городов даёт тот же пояс, иначе — название зоны («Екатеринбург, UTC+5»). Смещение берётся на момент `at` (`Intl`, `longOffset`), поэтому возможный будущий перевод часов отобразится верно.
