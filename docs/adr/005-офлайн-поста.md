# ADR-005. Офлайн поста охраны и синхронизация

Статус: принято.

## Контекст

В режиме «на объекте» (ADR-011) посты ходят к серверу по локальной сети, и обрыв интернета их не касается; офлайн-режим нужен при отказе сервера, плановом обновлении, обрыве LAN до поста и в режиме «облако». Пост должен работать без сервера не меньше смены (8 ч, `13_`), сценарий 29: связь пропала на 30 мин, 5 въездов отмечены по кэшу, после связи — синхронизированы, лимиты пересчитаны. Шлагбаум всегда можно открыть вручную; машина физически въезжает независимо от того, что знает сервер. Конфликты — администратору.

## Решение

### Что лежит на устройстве (Dexie / IndexedDB, база `oxrana-gate-<gateId>`)

| Хранилище | Содержимое | Обновление |
|---|---|---|
| `meta` | `gateId`, `siteId`, `snapshotAsOf`, `lastEventId`, версия движка | при каждой синхронизации |
| `rules` | `RuleSet` целиком (ADR/RULES_ENGINE §1) — на объекте это килобайты | `rules.changed` или раз в 10 мин |
| `passes` | действующие пропуска объекта: `approved` с `valid_to ≥ now − 24 ч` или `permanent`, плюс `pending_approval` (чтобы показать «на согласовании») | полная загрузка при старте и раз в час; дельта `GET /gate/passes?updatedSince=` по SSE `pass.*` |
| `openVisits` | открытые визиты объекта (`VisitView`) | `visit.*` события; полная перезагрузка вместе с `passes` |
| `queue` | очередь у ворот | `queue.*` |
| `pendingActions` | локальные действия в порядке совершения | см. ниже |
| `decisions` | последние 200 вердиктов для «Отменить последнее» и журнала смены | локально |

Service worker (Workbox, `vite-plugin-pwa`): оболочка приложения — precache; API-ответы не кэшируются SW (данные — только через Dexie, чтобы не было двух источников).

### Как считается вердикт офлайн

`engine.evaluate` с `rules` из кэша, `occupancy = countOccupancy(openVisits ∪ локальные check_in − локальные check_out)`, `now` = часы устройства. На экране — полоса «Нет связи — данные на 14:02 (12 мин назад)». Поведение по видам вердикта офлайн:

| Вердикт по кэшу | Офлайн-действие |
|---|---|
| 🟢 allow / 🟠 overage | «Впустить» доступна, визит создаётся локально (`method: 'sync'` после синхронизации) |
| 🟡 wait по лимиту | остаётся `wait` — лучше подождать, чем превысить. Кнопки «Запросить исключение» нет (нет связи с админом), есть «PIN старшего смены», если включён |
| 🟡 wait по времени | `wait` |
| 🔵 wrong_gate / 🔴 deny | как онлайн |
| выезд | всегда доступен, в том числе «выезд с отметкой» |
| «Машина без пропуска» | кнопка показывает «Нет связи — запрос уйдёт при восстановлении»; запрос ставится в очередь, водитель ждёт или звонит |

### Очередь действий и синхронизация

```ts
interface PendingAction {
  id: string;            // uuid устройства — ключ идемпотентности на сервере
  seq: number;           // монотонный на устройстве
  type: 'check_in'|'check_out'|'refuse'|'redirect'|'undo'|'gate_request'|'passage';
  passId?: string; plateNorm?: string; direction;
  clientAt: Instant;     // часы устройства
  localVerdict: Verdict; // что показал кэш (пишется в gate_decisions как offline=true)
  reason?: string;
}
```

- Онлайн действия идут тем же путём: `POST /gate/actions` с тем же `id` — поэтому код один, офлайн — просто задержка отправки. Ответ сервера содержит серверный вердикт и `visitId`.
- При восстановлении связи клиент отправляет очередь **по одному, по порядку `seq`** (`POST /gate/actions:sync` батчем, но сервер обрабатывает последовательно и отвечает по каждому). Повтор с тем же `id` — идемпотентен.
- Сервер для каждого действия: `evaluate` с `now = clientAt` (для текста причин и флагов) и текущим состоянием БД, затем применяет **правила разрешения конфликтов**:

| Ситуация при синхронизации | Решение сервера |
|---|---|
| check_in, лимит теперь превышен | **Визит открывается всё равно** (машина физически внутри), `flags += offline_over_quota`, событие `visit.opened`, уведомление администратору «въезд офлайн сверх лимита» |
| check_in, у пропуска уже есть открытый визит (отметили с другого устройства/КПП) | дубль не создаётся, действие помечается `merged`, ответ клиенту `already_open` |
| check_in по пропуску, который за это время отменили | визит открывается, `flags += pass_cancelled_meanwhile`, уведомление админу |
| check_out без открытого визита | визит создаётся сразу закрытым, `flags += no_checkin` |
| check_out, визит уже закрыт другим КПП | `merged`, ничего не меняется |
| undo для действия, которое сервер ещё не видел | оба действия аннулируются, в журнал — пара записей |
| `clientAt` расходится с `receivedAt` больше чем на 5 мин при наличии связи до этого | действие принимается, `gate_decisions.client_at` сохранён, уведомление администратору «часы на посту расходятся» |
| действие старше `retentionDays` или пропуск не найден вовсе | действие записывается в `gate_decisions` как `offline=true, action=none` с пометкой, уведомление админу |

- После успешной синхронизации клиент перечитывает `openVisits` и `queue` целиком (а не доверяет своим дельтам) и сбрасывает `pendingActions`.
- Сервер в ответ на каждое действие пишет **два** вердикта в `gate_decisions`: локальный (`offline = true`) и серверный — админ видит, что показал пост и что было на самом деле.

### Ограничения и ПДн

- Кэш содержит номера и ФИО пешеходов (нужны для поиска). База Dexie удаляется при отзыве устройства (команда `device.revoked` по SSE или при первом запросе после отзыва) и при выходе из киоска. Диск поста — ответственность оператора (физический доступ только у охраны); это записано в политике ПДн.
- Снимок — только свой объект и только действующие пропуска; история визитов на устройстве не хранится.

## Альтернативы

- **CRDT / полная репликация** (ElectricSQL, PowerSync): избыточно — модель конфликтов у нас одна и простая («факт важнее лимита»), а инфраструктуры добавилось бы много.
- **Запрет действий офлайн** (только просмотр): охрана всё равно откроет шлагбаум, и визит потеряется — хуже, чем принять его с флагом.
- **Отклонять офлайн-въезды сверх лимита при синхронизации**: машина уже внутри, отказ создаёт ложное состояние.
- **Кэшировать API-ответы в service worker**: два источника правды и невозможность посчитать занятость локально.

## Последствия

- Сценарий 29 закрывается интеграционным тестом: 5 действий с `clientAt` в прошлом → 5 визитов, занятость пересчитана, при превышении — флаги и уведомление.
- Любая новая кнопка поста обязана проходить через `PendingAction` — иначе она не работает офлайн; это правило архитектуры поста.
