# ADR-017. API ядра (этап 4)

Статус: принято (10.10.2026, этап 4). Реализует ARCHITECTURE §2–3, ADR-004, 005, 006, 007 (в части проверки прав маршрутов), 009 (дополнение о поясах); уточняет места, где реализации пришлось выбирать.

## Контекст

Этап 4 — модули `org`, `tenants`, `rules`, `passes`, `gate`, `occupancy`, `audit`, outbox и SSE, часы, тест-матрица прав с фиктивным актором (вход — этап 5). По ходу пришлось решить: как проверять права, которые зависят от тела запроса; как читать справочники без отдельного права; где хранить идемпотентность действий поста; как не получить взаимную блокировку пула при транзакции въезда; что считать дублем и когда арендатор правит пропуск сам, а когда — заявкой.

## Решение

### 1. Актор и область (до этапа 5 — фиктивный)

`Actor` (`apps/api/src/actor.ts`): вид (`user` / `gate_account` / `system`), организация, права, область — `siteIds` (`null` — вся организация), `tenantIds` (`null` — сотрудник оператора или пост; список — пользователь арендатора), `gateId` и `deviceId` учётки поста. Хук прав проверяет только наличие права у маршрута; область проверяет сервис: чужая организация — 404 (запись не видна, RLS), свой объект вне области или чужой арендатор — 403 (ADR-007). На этапе 5 актора будут строить сессия и токен устройства из назначений ролей; права пока — объединение прав всех назначений.

### 2. Права маршрутов

- `config.permission` — одно право **или список «любое из»**. Там, где право зависит от тела запроса, маршрут объявляет список, а сервис уточняет: тип пропуска — `pass.create.<тип>`, вид действия поста — своё право (`visit.check_in`, `visit.check_out`, `gate.refuse`…), чужой арендатор — `pass.create_for_any_tenant`. Уточнение — тот же ответ `403 forbidden` с полем `permission`.
- `config.authenticated: true` — нужен вход, но не отдельное право: только **GET** справочников объекта (объекты, зоны, КПП, доки, типы, арендаторы — со своей областью, пояса, `GET /org`, свои настройки). Изменение всегда требует права; `authenticated` на не-GET маршруте не стартует.
- Новое право `profile.manage_own` — свои настройки («показывать ещё и моё время»); добавлено во все пользовательские шаблоны, у поста его нет.
- Хук ведёт реестр маршрутов `app.routeAccess`; тест-матрица (`apps/api/test/permissions.*`) проверяет каждый маршрут × каждую роль-шаблон × «без входа» и держит снимок реестра (метод, путь, право) — изменение права маршрута видно в ревью.

### 3. Пути

В Fastify после параметра нельзя поставить `:глагол` (`/passes/{id}:approve` превращается в параметр `id::approve`). Действия над записью — подресурсом: `POST /passes/:id/cancel`, `POST /change-requests/:id/approve`, `POST /gate-requests/:id/approve`; над коллекцией — так же: `POST /passes/batch`, `POST /gate/actions/sync`. Записи `:batch`, `:approve`, `:sync` в ТЗ и ARCHITECTURE читать так. КПП поста в путях нет: `/gate/*` берёт его из учётки (ADR-007).

### 4. Транзакция запроса, аудит, события

`ctx.tx(scope => …)` — одна транзакция с `set local app.organization_id` (RLS), явный фильтр по организации в каждом запросе; `scope.audit()` и `scope.emit()` пишут в той же транзакции. **Внутри транзакции — только её соединение**: срез правил (`RuleSetCache`, 5 с) загружается тем же соединением; второе соединение из пула при маленьком пуле давало бы взаимную блокировку (транзакция держит блокировку арендатора и ждёт соединение, которое занято транзакцией, ждущей эту блокировку). Изменения правил сбрасывают кэш сразу после коммита в этом процессе и по `rules.changed` из LISTEN — в остальных. Payload события проверяется строгой схемой из `contracts/events.ts` и на поля с ПДн — ошибка здесь означает ошибку программы.

### 5. Справочники — одной фабрикой

`core/crud.ts`: список, карточка, создание, PATCH только реально изменённых полей (CLAUDE.md п. 5), удаление — мягкое при `deleted_at` и жёсткое без него, с показом «где используется» (`findUsages`) и подтверждением `?confirm=true` (п. 10), аудит «было → стало» с подписями ссылок (п. 6), событие `rules.changed` / `tenant.changed`. Ключи тела совпадают с полями Drizzle; особое — `prepare` (ссылки на записи того же объекта, вычисления) и `afterWrite` (наборы типов). Нарушение уникальности или exclusion — понятная ошибка с полем, не 500.

### 6. Действия поста и идемпотентность

Таблица `gate_actions` (только insert): id устройства, тип, итог (`applied` / `merged` / `rejected`), сохранённый ответ, отпечаток тела. Действие выполняется под `pg_advisory_xact_lock` по своему id: повтор с тем же id возвращает сохранённый ответ (`replayed: true`) и ничего не делает; тот же id с другими данными — `409 idempotency_conflict`. Ошибка (нет права, нет причины) ничего не записывает — повтор выполнится заново. «Ждать» — тоже итог (`rejected`, `code: wait`): новая попытка «Впустить» — с новым id.

### 7. Въезд, выезд, очередь, отмена

- **Въезд** (`checkIn`, ADR-006): блокировка арендатора → свежие открытые визиты → занятость `countOccupancy` (та же функция, что на посту офлайн) → точка внедрения теста → повторный `evaluate` → визит. Визит вставляет только `packages/db/src/queries/visits.ts` (архитектурная проверка). `visits.exception_id` — только исключение, снявшее лимит: такой визит место не занимает. Уже на территории — `merged`, второй визит не открывается. Команда шлагбауму — только в этой транзакции.
- **Ждать по жёсткому лимиту** ставит пропуск в `gate_queue` по самому тесному лимиту. Освобождение места (выезд, отмена въезда) — событие `queue.slot_freed` первым ещё не оповещённым в очереди, по числу свободных мест; SSE отдаёт его только посту, где стоит машина (сценарий 40).
- **Выезд** блокировку не берёт: `update … where time_out is null` делает двойной выезд с двух КПП идемпотентным (`merged`). Нет открытого визита — «выпустить с отметкой» с обязательной причиной: визит создаётся сразу закрытым, `no_checkin` (сценарий 16). Разовый после выезда — `used`.
- **Отмена** — в окне `undoWindowSec` от времени действия, только своего поста и один раз: отмена въезда закрывает визит с флагом `undone`, отмена выезда снова открывает визит и возвращает разовый в «действует»; в журнале КПП — оба решения.
- **Внутренний пост**: только проход (`gate_passages`), въезд и выезд там — ошибка вида КПП.

### 8. Офлайн-синхронизация (сервер, ADR-005)

`POST /gate/actions/sync`: действия по `seq`, каждое — своей транзакцией (блокировки не держатся на всю очередь, ошибка одного не отменяет остальные). Вердикт — с `now = clientAt`; въезд открывает визит всегда — машина уже внутри: сверх лимита `offline_over_quota`, отменённый пропуск `pass_cancelled_meanwhile`; время въезда — время устройства. В журнал КПП пишется и вердикт поста (`localVerdict`), и серверный. Уведомления администратору о флагах — этап уведомлений.

### 9. Пропуска

- «Не в прошлом» — только при создании и при изменении начала (ADR-009 п. 6), с допуском 10 минут на задержку формы; текст ошибки — во времени объекта с подписью пояса.
- Разовый — не дольше `singlePassMaxHours`; многоразовый — от `multiPassMinDays` до `multiPassMaxDays` местных календарных дней; постоянный — без окончания. Окно прибытия обязательно по политике окна, кроме исключения, снимающего проверку окна (X5 24/7).
- Тип с лимитом 0 по всем лимитам арендатора не оформляется (такой пропуск не пропустят), кроме исключения, снимающего лимит; в подсказках формы такие типы не показываются.
- Политика согласования: своя у арендатора важнее политики объекта; запрет — ошибка со ссылкой на настройку; обязательный комментарий — «Укажите, для чего и зачем нужен пропуск»; «на согласовании» — `pending_approval`. **Нет политики на сочетание — без согласования** (вопрос Q-55).
- Дубль — exclusion в БД под SAVEPOINT: ошибка называет мешающий пропуск и его срок; тот же номер у другого арендатора — предупреждение в ответе.
- **Правка**: только присланные и реально изменённые поля; у начавшегося пропуска — с причиной (сценарии 19, 20). Пользователь арендатора меняет номер, тип и срок согласованного пропуска **заявкой на изменение**, если пропуск уже начался или согласовывался по политике (A8, сценарий 41); остальные поля того же запроса применяются сразу. Тот же номер в другой записи изменением не считается. Одобрение заявки меняет тот же пропуск; в истории — заявка и изменение.
- Пакет: SAVEPOINT на строку, «создано N из M» с причинами по строкам; предпросмотр (`dryRun`) проходит тот же путь, включая дубли, и откатывается.
- Страница водителя: токен создаётся сразу, в ответе — один раз, в БД — хэш; срок — конец пропуска + сутки (постоянный — год).

### 10. «Машина без пропуска» (сценарий 15)

Пост создаёт `gate_request` (срок ответа — `gateRequestTimeoutMin`); отвечает человек (учётка поста свой запрос не одобряет): «Оформить» создаёт разовый пропуск от момента ответа на срок разового (или до указанного окончания) с окном прибытия «с момента ответа» — машина уже у ворот; пропуск проходит обычные проверки и политику арендатора. Ответ после срока — «запрос закрыт».

### 11. SSE

`GET /sites/:siteId/events` и `GET /gate/events`: подписка на хаб ставится до чтения таблицы (событие между ними не теряется), `Last-Event-ID` дочитывает до 1000 событий, больше — `event: resync`. Видимость: пост и сотрудники оператора — все события объекта; пользователь арендатора — события своих арендаторов и общие события объекта; `queue.slot_freed` — только посту первой машины. Слушатель LISTEN стартует с сервером и без БД не роняет его (переподключение в фоне). Открытые потоки закрываются в `preClose`.

### 12. Пояса (ADR-009, дополнение)

`POST /sites` без `timezone` берёт пояс организации (подстановка по контракту, ответ показывает пояс; источник — в аудите), нет пояса — `timezone_required`; подсказка по адресу — `GET /timezones?address=`, сама не подставляется. Смена пояса — `POST /sites/:id/timezone` с причиной и `confirm: true`, иначе `409` с текстом последствий. Подпись «Челябинск, UTC+5» — `timezoneLabel` из contracts.

### 13. Логи

В pino редактируются номера, ФИО пешеходов и водителей, телефоны (ARCHITECTURE §7.4); адрес запроса пишется без строки запроса (поиск по номеру).

## Не вошло в этап 4 (перенесено явно)

- Согласование пропусков на согласовании (одобрить / отклонить / «с изменениями», эскалация) и запросы исключений (`override_requests`) — этап 5 (сценарии 24, 42; чтение одобренных исключений в транзакции въезда уже есть).
- Учётка КПП при создании КПП и привязка устройств — этап 5.
- Чёрный список, цели визита, парковочные участки, пакетный ввод доков — API вместе с экранами админки (этап 6).
- Автопарк арендатора и страница водителя — этап 7.
- «Отменить свои» для роли «Арендатор — заказчик» сейчас — любой пропуск своего арендатора (вопрос Q-56).

## Альтернативы

- **Отдельный маршрут на каждый вид действия поста** (`/gate/check-in`, `/gate/check-out`…): матрица проще, но ADR-005 требует один путь для онлайна и офлайна; уточнение права в сервисе покрыто вариантами матрицы.
- **Отдельное право на чтение справочников** (`site.view`): его пришлось бы выдавать всем ролям; справочники объекта не секретны внутри области, а область проверяет сервис.
- **Идемпотентность колонкой в `gate_decisions`**: одно действие пишет до двух решений (офлайн), а повтор должен вернуть ответ, а не только «уже было».
- **Загрузка RuleSet отдельным соединением**: при пуле из 2 соединений (как в тесте сценария 37) транзакции, держащие блокировку арендатора, ждали бы соединение, занятое транзакцией, которая ждёт эту блокировку.
- **Автоматический перенос номера в заявку без частичного применения**: арендатор правил бы комментарий и номер одной формой и получал бы непонятный отказ; частичное применение с явным `applied` и `changeRequest` честнее.

## Последствия

- Новый маршрут попадает в матрицу прав и снимок реестра сам; его право видно в ревью.
- Клиенты (кабинет, пост) получают подсказки и ошибки с полем и ссылкой на настройку — формы этапов 6–8 опираются на них.
- Этап 5 заменяет фиктивного актора настоящим без изменения сервисов: им нужен только `Actor`.
