# Платформа пропускного режима — правила проекта

Платформа ведёт въезд и пребывание транспорта и людей на территории с несколькими арендаторами (складские комплексы, промзоны). Аналог PASS24.online, но без его обходных путей: квоты, маршруты по КПП и места назначения — независимые правила, а охранник получает однозначный вердикт-светофор. Первый объект — ЛЦ «Радонежский» (Челябинск, UTC+5), оператор ООО «Интеграция». Архитектура — сразу мультиобъектная и мультиарендная (SaaS).

## Где что лежит

- `docs/spec/` — ТЗ, файлы 00–16. **`16_дополнения_и_уточнения.md` главнее остальных** при расхождении. Начинать с `00_README.md`.
- `docs/reference/` — справочные материалы (PASS24, договоры, охрана, Excel лимитов). Большие файлы: открывать только нужный раздел, целиком не читать.
- `docs/ARCHITECTURE.md` — компоненты и потоки; `docs/DATA_MODEL.md` — схема БД (источник истины для миграций); `docs/RULES_ENGINE.md` — контракт движка; `docs/GLOSSARY.md` — термины; `docs/ROADMAP.md` — этапы и статусы; `docs/QUESTIONS.md` — открытые вопросы; `docs/adr/` — решения с альтернативами (индекс в `docs/adr/README.md`).

Читай только файлы, нужные для текущей задачи. ТЗ целиком — только на этапах проектирования.

## Язык

- Интерфейс, сообщения об ошибках, документация, коммиты — **по-русски**.
- Код, идентификаторы, таблицы, API — по-английски.
- Термины — строго по `docs/GLOSSARY.md` (один термин на одно понятие: никаких «разовый / одноразовый», «временный» = «многоразовый»). Названия объекта, КПП и арендаторов (Радонежский, ДНС, КПП-1…) живут только в сиде и документах, в коде приложения их нет.

## Стек (утверждён в ADR-001; версии — там)

- TypeScript 7 strict везде; Node.js 22 LTS; монорепо pnpm workspaces без оркестратора сборки (ADR-002). Линт и формат — Biome.
- Сервер: Fastify 5 + zod 4 (валидация и OpenAPI из одних схем). Пароли — argon2id. Логи — pino с редакцией ПДн.
- БД: PostgreSQL 16 (+ pg_trgm, btree_gist, citext), Drizzle ORM, SQL-миграции в репозитории, RLS по организации (ADR-003). Фоновые задачи — pg-boss. Realtime — outbox `domain_events` → `LISTEN/NOTIFY` → SSE (ADR-004). Redis не используем.
- Веб: React 19 + Vite, TanStack Router + Query, shadcn/ui + Tailwind 4, react-hook-form + zod. Даты в UI — date-fns + @date-fns/tz; в движке — только `Intl` (ADR-009).
- Пост охраны: отдельное PWA-приложение (vite-plugin-pwa), снимок данных и очередь действий в IndexedDB через Dexie (ADR-005).
- Тесты: Vitest (unit без БД; интеграция с реальным Postgres — БД на worker из шаблона), Playwright (E2E, Chromium предустановлен).
- Развёртывание: один дистрибутив (Docker Compose), режимы «на объекте» (основной: сервер в ЛЦ, посты по LAN, доступ извне через VPS-шлюз с WireGuard) и «облако» (ADR-011). Наружу только веб и API; внешние сервисы — только исходящие соединения (Telegram — long polling). Тестовый стенд на VPS заказчика — первая часть режима «облако»: `deploy/`, `docs/STAND.md`, ADR-019. **Сеть из РФ ненадёжна:** Docker Hub отвечает 403, `download.docker.com` ненадёжен, `raw.githubusercontent.com` временами недоступен — образы и файлы везём с runner (сборка в CI, доставка по SSH), на объекте и на серверах в РФ не рассчитываем на прямые загрузки.

## Несущие правила архитектуры

1. **Движок вердикта — отдельный пакет из чистых функций**: без БД, сети и системных часов; время передаётся параметром. Один и тот же код работает на сервере и на посту офлайн. Каждый вердикт возвращает причины и trace (какие правила проверены и чем закончились).
2. **Квота ≠ маршрут ≠ место назначения.** Понятия «адрес» как носителя лимита нет.
3. **Квоты считаются по открытым визитам** (въехал и не выехал), а не по пропускам. Проверка квоты и запись въезда — одна транзакция с advisory lock по арендатору (ADR-006): две машины на последнее место не проходят. Все пути создания визита идут через `checkIn()`.
4. **Время:** хранить в UTC (`timestamptz`), показывать в поясе объекта и подписывать пояс. Пояс браузера и сервера не использовать никогда.
5. **Редактирование — PATCH только изменённых полей.** Формы правки без дефолтов, заблокированы до загрузки данных.
6. **Аудит каждого изменения:** было → стало, кто, с какого устройства, причина. В журнальных записях — снимки названий на момент события.
7. **Права атомарные, проверяются на сервере.** Каждый маршрут объявляет `config.permission`, покрыт тест-матрицей 403 (ADR-007). Новая роль создаётся без прав. **Новое право → миграция, выдающая его ролям по шаблонам** (`pnpm --filter @oxrana/db role-sync-sql`, ADR-007): существующие организации (стенд) создавались до права; владелец (`org_owner`) получает все права при сборке актора. «Отметить въезд/выезд» и «редактировать пропуск» — разные права; администратор объекта не нажимает «Впустить».
8. **Ошибки структурированные:** `{code, message, field, settingLink}`. Текст называет причину и где её исправить. Никаких молчаливых подмен значений и ложных «сохранено».
9. **Мультиарендность:** каждая запись несёт `organization_id`; запрос фильтруется по ней явно, RLS — вторая линия. Оператор объекта — тоже арендатор (`is_operator`).
10. **Справочники удаляются мягко**, с показом, где элемент используется.
11. **Оборудование** (камеры номеров, шлагбаумы, QR-сканеры, СКУД) подключается только через слой адаптеров и агента КПП (`docs/spec/16_…`, раздел D). Ядро и экран поста не знают марок. В MVP — контракты, таблицы и симуляторы, без драйверов.

## Среда разработки

Облачные сессии Claude Code (claude.ai/code): Ubuntu 24.04, Node 22 + pnpm 10, PostgreSQL 16 как системный кластер (выключен при старте: `pnpm db:up` = `service postgresql start` + роли и базы, ADR-010). **Docker-демон в сессии недоступен** — Testcontainers и compose не использовать; интеграционные тесты идут на локальном кластере. Playwright: `playwright install` не запускать, браузеры в `/opt/pw-browsers`. Каждая сессия работает в своей ветке; результат попадает в `main` через PR.

## Правила интерфейса

- Пост охраны: одна учётка на КПП, без личных PIN (`16_…`, A11); светофор (🟢 🟡 🔵 🔴 🟠), одна фраза причины, одна большая кнопка; кнопки ≥ 64 px; поиск по цифрам номера, автоочистка после действия; обновление в реальном времени без F5.
- Недоступный элемент не прячется — показывается неактивным с причиной. Исключение — настройка организации «Вести договоры» (выключена: договоры скрыты везде, ADR-021).
- Даты и время — только свои компоненты `DateInput` / `TimeInput` / `DateTimeInput` (`ДД.ММ.ГГГГ`, `ЧЧ:ММ` независимо от языка браузера); нативных `<input type="date|time">` нет. Пакетная проверка (`dryRun`) идёт сама при вводе, кнопка одна (`useAutoPreview`).
- Где вводится список (номера, арендаторы, доки) — есть пакетный ввод и вставка из Excel.
- Подсказки показываются в форме до сохранения («Фура → КПП-2», «Грузовые 25/25 — машина будет ждать»).
- Пользователь видит только те категории, типы и действия, которые ему доступны.

## Как работать

- Большая задача — сначала короткий план, потом код. Этап = одна сессия по `docs/ROADMAP.md`; изменение схемы — сначала `docs/DATA_MODEL.md`, потом миграция.
- Каждый сценарий приёмки (`docs/spec/14_…` и раздел C в `16_…`), который закрывает этап, — автотест.
- Перед тем как сказать «готово»: прогнать typecheck, lint и тесты, все зелёные.
- CI не ждать через фоновые `sleep` и опрос — каждое пробуждение тратит токены. Достаточно локальных проверок перед «готово»; результат CI смотрим в PR.
- Коммиты маленькие и осмысленные, по-русски. В конце этапа — обновить статус в `docs/ROADMAP.md`; архитектурное решение — в ADR.
- Новую зависимость добавлять только с причиной (одна строка в описании коммита).
- Требование неясно или противоречит ТЗ — не выдумывать: записать в `docs/QUESTIONS.md` с вариантами и рекомендацией, спросить.
- Секретов в репозитории нет: только `.env.example`. Реальных персональных данных тоже нет: телефоны, ФИО и e-mail в сиде и тестах — выдуманные. ПДн не пишутся в логи и в `domain_events.payload`.
- **В конце каждого ответа — краткий отчёт:** что сделано; как проверить (команды или шаги); что не сделано или сделано иначе, чем просили, и почему; вопросы ко мне.

## Демо-данные

Сид «ЛЦ Радонежский» — **только для автотестов и разработки** (ADR-016): на реальном сервере платформа стартует чистой (организация + учётка владельца), объект заказчик настраивает сам через интерфейс. Сид — по `docs/reference/лимиты_для_сида.md`: КПП-1, КПП-2, КПП офис (одна учётка на КПП); доки; 11 арендаторов + оператор «Интеграция»; лимиты; исключения (автобус ДНС, X5 24/7); правила пешеходов. Значения правдоподобные, пометок `ПРОВЕРИТЬ` в демо-данных нет.

## Команды

Всё запускается из корня. Облачная сессия готовит окружение сама (SessionStart-хук: `pnpm install`, `pnpm db:up`, `pnpm db:migrate`, `pnpm db:seed`); вручную — тот же набор.

| Что | Команда |
|---|---|
| Установка зависимостей | `pnpm install` |
| Поднять PostgreSQL, роли и базу `oxrana`; создать `.env` из `.env.example` | `pnpm db:up` (идемпотентно, ~3 с) |
| Применить миграции (под `oxrana_owner`) | `pnpm db:migrate` |
| Демо-объект «ЛЦ Радонежский» (идемпотентно: повтор ничего не дублирует и не меняет) | `pnpm db:seed` |
| Пересоздать базу с нуля: миграции и сид | `pnpm db:reset` |
| Чистый старт на пустой базе: организация, шаблоны ролей, владелец; печатает одноразовую ссылку установки пароля (ADR-018) | `pnpm bootstrap --org "…" --slug … --timezone Asia/Yekaterinburg --owner-name "…" --owner-email …` |
| Запуск для разработки: API :3000, web :5173, gate :5174 | `pnpm dev` |
| Сборка web, gate и API | `pnpm build` |
| Дымовая проверка собранного API (после `build`) | `bash scripts/smoke-build.sh` |
| Типы (`tsc -b` по project references) | `pnpm typecheck` |
| Линт и формат (Biome) | `pnpm lint` · исправить автоматически: `pnpm format` |
| Юнит-тесты, без БД (включая компонентные) | `pnpm test:unit` |
| Компонентные тесты React в jsdom (`packages/ui`, `apps/web`) | `pnpm test:components` |
| Покрытие `engine` и `plates` (порог 95 % строк) | `pnpm test:coverage` |
| Интеграционные тесты на реальном PostgreSQL (шаблон `oxrana_test_template` с миграциями, своя копия базы на каждый файл) | `pnpm test:integration` |
| Все тесты Vitest | `pnpm test` |
| E2E Playwright (сами поднимают API на чистой базе `oxrana_e2e`, web, gate на портах 3100/5273/5274) | `pnpm test:e2e` |
| Один тест | `pnpm exec vitest run путь/к/файлу.test.ts` |

| Проверка «готово» | `pnpm typecheck && pnpm lint && pnpm test` (а при правке `deploy/` и workflow — ещё `pnpm test:deploy`, `shellcheck -x -P SCRIPTDIR deploy/oxranactl deploy/setup-vps.sh deploy/test/*.sh deploy/test/fakes/*`, `actionlint`) |

Где что: `apps/api` (Fastify: `src/core` — транзакция запроса с аудитом и outbox, фабрика справочников; `src/auth` — пароли, токены, CSRF, ограничение попыток, актор из сессии и токена устройства; `src/cli` — чистый старт; `src/modules/*` — модули; `src/realtime` — SSE; `src/files` — `FileStore` (файлы договоров, ADR-021); `src/modules/blacklist` и `src/modules/sandbox` — чёрный список и песочница правил; тесты `test/scenarios` — сценарии приёмки на демо-объекте, `test/permissions.*` — матрица прав, субъекты тестов — настоящие сессии и токены устройств из `test/support/harness.ts`), `apps/web` (кабинет и админка: оболочка `routes/admin.tsx`, карточки справочников `src/components/cards`, мастер `components/wizard.tsx`, готовность шагов `lib/steps.ts`) и `apps/gate` (Vite + TanStack Router), `packages/{contracts,engine,plates,db,ui}` (`ui` — Tailwind 4, компоненты в стиле shadcn, формы правки, пакетный ввод, время объекта; ADR-020), `scripts/` (БД, архитектурные проверки), `deploy/` (стенд: Dockerfile, compose, Caddyfile, `oxranactl`, `setup-vps.sh`, `test/` с поддельными docker и curl), `e2e/`. В `packages/db`: `src/schema` (Drizzle), `migrations/` (0001 генерируется, ручное — отдельными файлами), `seed/` (единственное место с названиями объекта), `test/` (harness тестовых баз). В `packages/engine/test/fixtures` — замороженный срез правил демо-объекта (ADR-015), в `scripts/check-engine-purity.ts` — запрет часов, сети и пояса среды в `engine` и `plates`. Решения по устройству каркаса — ADR-013. Новая внешняя зависимость — только через `catalog:` в `pnpm-workspace.yaml`, версия точная.
